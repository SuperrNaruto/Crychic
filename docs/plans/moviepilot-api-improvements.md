# MoviePilot API 功能改进计划

更新日期为 2026-10-12。本计划按日常使用价值排序，不以开发成本排除功能。目标是在现有确定性会话流程上，改善资源搜索、订阅设置、下载控制、状态核对与缺集处理。

当前第 1、2、4、5、6、7、8、9 项与第 6 项前置的原生通知接入已交付；第 3 项随后按主人决定退役。下一项是第 10 项「同系列库存与补齐计划」，第 10 至 12 项及高级组合筛选仍为计划。原编号保留，各项独立交付；计划保存不授权代理实施功能、部署或对真实 MoviePilot 执行搜索与写操作。

历史顺序为 2026-10-09 实施第 1 项，2026-10-10 实施第 2、3、4 项，2026-10-11 完成第 5 项及原生通知接入，随后删除本地请求归属与第 3 项，2026-10-12 实施第 6、7、8、9 项。通知最初按主人要求只写计划，后经授权实施并上线，主人实机验收记录见下文。

本轮只按最新项目规则更新计划与 README。下文第 1 至 5 项的实施记录、原生通知首次迁移设计和历史版本来源用于追溯，涉及请求归属、自建通知及旧配置的安排以本文当前原则为准；历史检查结果不作为本轮重新验证的结果。

## 后续开发原则

- 采用「现有 Crychic + 原生 API 优先 + MP 插件补足能力」。Go 继续负责平台接入、白名单、会话、最终确认、展示及安全投递，不将整个 Crychic 重写成 MP 插件。
- 各功能先核验原生 API。能够可靠满足需求时直接使用；存在明确的能力、事件、上下文或可靠性缺口时，记录缺口与采用理由，再由 MP 侧 Crychic 插件补足。
- 插件保持薄适配层，优先使用公开 SDK 和受支持的扩展点，复用原生业务实现；不重写 MP 业务引擎，也不要求所有请求经过插件。
- 后续新增能力默认核对 MP 最新稳定版，已有交付与历史来源保留；仅在目标部署存在明确版本差异时增加针对性验证。
- 插件接入不放宽鉴权、隐私、最终确认、未知结果不重放或真实服务操作边界。完整分工见 [架构参考](../agent-reference/architecture.md#后续开发原则)。

## 当前用户与权限范围

2026-10-11 起按单一信任域运行，白名单内用户同等管理 MP 内全部订阅与下载，包括网页端创建的订阅。管理员 API key 和插件身份均不能替代聊天用户的白名单授权；会话仍按用户、聊天及话题隔离，写前继续核验订阅复合身份、下载器实例及目标。

第 3 项「我的请求与异常」已退役，`/requests`、本地请求归属、到货事实、最近完成及仅为它们服务的整理历史和失败历史读取已删除。后续条目不得为权限控制、库存汇总或异常提示重建这些本地记录。状态展示按需核对 MP 的可信事实，通知种类、时段与受众由 MP 决定；白名单内同等管理业务资源不扩大通知接收范围。

多用户隔离等 MP 官方支持按用户的 API 凭据后再设计。保留 `flow.Actor`，届时在 `internal/app` 按 Actor 选择凭据或 Backend，归属沿用 MP 自身的用户体系。旧 `requests.json` 和 `requests.json.pre-native` 不再读取，也不删除或改写。决策理由与扩展边界见 [用户与权限模型](../agent-reference/architecture.md#用户与权限模型)。

## 每项功能的能力选择与交付条件

每项开始实现前，先完成以下核验并写入该项实施记录，不把核验另列为必须上线的前置阶段。

1. 记录 MP 最新稳定版、官方源码或文档来源，以及目标部署已知的版本差异。依赖外部 API、SDK 或 CLI 细节时先按 Context7 规程查询，MoviePilot 行为不明确时补查对应版本源码。
2. 核验原生 API 的目标身份、认证、输入、返回、业务副作用和失败语义。能可靠满足需求时由 Go 直接调用；新增命令、配置、服务和持久状态只保留功能必需部分。
3. 原生 API 不足时列明能力、事件、上下文或可靠性缺口，说明为何现有只读核对不能满足，再确定最小插件扩展。插件只补该缺口，复用 MP 原生业务；公开扩展点不足时记录内部适配范围、宿主版本与隔离宿主 E2E 条件。接入不可靠时缩小功能或停止该项，不猜测关联、不绕过确认。
4. 在代码前枚举外部失败方式并确定真实行为覆盖缺口。Go 使用真实 app 对外部 HTTP fake；插件适配点使用真实 MP 隔离宿主。每个新增主场景保存可重复比对的脱敏 transcript，不增加内部 mock、单元测试或冗余测试。
5. 独立提交可用功能，记录检查结果、未验证部分与回退方法。插件停用不能拖垮原有 API 功能；读取失败不重跑业务，未知写入不自动重放。真实搜索、写入与渠道配置由主人手测，代理不代为执行。

实施条目中的接口保留自既有计划与历史源码核验，作为后续核验候选。本轮未重新核对 MP 最新稳定版，不把候选接口或插件方向写成已实现、已兼容或已验收。

## 第 2 项实施前验收设计

本节及其实施结果记录当时的请求者权限与通知 watch 设计；当前订阅管理面向全部白名单用户，旧 watch 相关逻辑已退役。

2026-10-10 开始订阅条件编辑。只编辑请求者自己的订阅；草稿只在当前会话内存中存在，返回或取消不写 MoviePilot，最终确认只提交与打开编辑器时不同的字段。已有规则组和站点按需读取，不创建规则、不触发补搜。

Context7 的资料仍指向 `v3` 主线；本阶段以官方 `v3.1.1` 的 `subscribe.py`、`schemas/subscribe.py`、`application/filtering.py` 和订阅匹配源码复核。更新端点使用 `exclude_unset=True`，显式空值清除可选字符串；`note`、`lack_episode`、当前优先级等运行事实被公共写接口排除。编辑不能用重置进度来实现起始集或洗版变更。空规则组分别沿用普通订阅或洗版的全局组。

| 主验收场景 | 可信失败方式 | 原覆盖缺口与验收证据 |
| --- | --- | --- |
| 草稿与最小更新 | 未确认即写、未修改设置被覆盖、清空被当成省略、空集合误变全部禁用、选项编号或顺序改变 | 旧场景没有条件更新入口；真实聊天逐项编辑和预览，核对一次 PUT 的明确改动字段及未触及的后台字段 |

### 第 2 项实施结果

- 订阅详情新增请求者专属「编辑条件」，支持分辨率、质量、特效、已有规则组、站点、包含／排除字面关键词、起始集和普通／分集洗版／全集洗版。多选目录分页，草稿本地保存，最终预览确认一次写入；无新配置，不需要资源 Cookie。
- 包含／排除首版限制为单行字面关键词，`|` 分隔任一匹配，最多 256 字、12 项；不把 Go 正则当作 Python 正则校验器。原有复杂表达式保留或清空，复杂正则编辑留在 MoviePilot。选项、输入和确认有独立当前屏幕身份，旧编号、重复确认和返回不能复用已消费目标。
- 更新只发 `id` 和明确改变的字段，字符串清空用 null，集合清空用 `[]`。后台未触及设置和运行事实不回传；已选规则定义／站点、订阅复合身份、归属、可编辑条件和总集数会预检。仍不承诺后端原子 compare-and-write。
- 明确拒绝使用安全提示；408、缺少 `success`、半响应、跳转或未知结果只提供只读核对。不跟随更新重定向，不重放写入。普通与洗版各自读取正确的全局规则组。

### 第 2 项交互改进的实施前验收设计

本轮按已确认的交互评审改进，不新增 MoviePilot 接口或放宽写入边界。实现前先补或扩展下列真实 app 对 HTTP fake 的场景。

| 主验收行为 | 可信失败方式 | 验收归属 |

| 离开草稿 | 字段返回误丢修改、编辑菜单返回直接清空、取消没有保护、旧放弃按钮清掉新草稿、无修改也强制确认 | 扩展草稿场景；确认保留／放弃、字段提示恢复、零额外 PUT |

| 只读核对结果 | 未知写入无法核对站点和条件、读取失败当成功、其他值误称已生效、同 ID 换目标、旧确认被恢复、核对重新写入 | 扩展未知写入场景，新增逐字段核对场景；对原值／期望值／其他值／未知逐项显示，不依据原始敏感内容展示 |
| 保留冲突草稿 | 冲突清掉用户输入、未修改字段被旧快照覆盖、采用后台值仍发旧值、重新读取后旧选择和确认仍有效、超出最新集数范围 | 新增冲突处理场景；保留或采用后台逐项选择，显式接受处理结果后生成新确认，最终 PUT 只含仍需改动字段 |
| 目录变化 | 已选规则／站点变更清掉其他草稿、未重选仍跳过目录核验、失败读取消耗草稿 | 扩展现有目录场景；只返回编辑并保留草稿，重新选择后仍走原目录与身份预检 |

只读结果摘要与编辑草稿使用不同会话字段；摘要不能恢复为写入目标。核对结果只说明当前值是否匹配，不能据相等推断当时请求一定成功。沿用 10 分钟会话 TTL，不持久化敏感条件或结果摘要。退出确认只针对本条编辑消息的导航，新的显式命令仍按项目输入规则切换会话。

## 第 3 项实施前验收设计

本节保留已经退役功能的设计、实施与验证证据，原入口和本地记录均不再使用，也不作为后续条目的依赖。

本轮继续实现「我的请求与异常中心」，只增加 `/requests` 和首页入口。复用通知 watch 建立请求归属、现有列表分页和逐集进度；按需只读订阅、下载、整理队列与失败历史，不增加后台服务、事件总线、运行配置或自动修复。

核对官方 `v3.1.1` 源码后确认：`failure_stage`、`retry_exhausted`、`auto_paused` 属于整理历史；订阅 `execution_status` 只提供搜索阶段及错误是否存在。`recovery_action` 是自由文本，不是可直接信任的动作枚举。页面只按已知阶段映射固定建议，未知值保持未知；不展示错误正文、文件路径、资源名、实例名或其他请求人的身份。

跟踪中的请求只来自当前用户的本地记录；详情读取媒体库，列表不对所有请求逐个追加媒体库查询。失败历史每次至多检查最近 100 条，明确说明截断或读取不完整，未匹配不代表不存在异常。最近完成最多保留 50 条最小脱敏记录，随原有通知状态原子保存，只记录功能启用后已确认所需范围到货的结算；完成记录不证明媒体服务器当前可见，也不据不可靠的资源集数补出整包完成。

### 第 3 项续做时补充的验收边界

- 扩展现有下载身份场景。相同 hash 在队列中出现不同实例，或另一个实例缺少媒体身份，不能绕过歧义检查；移除不确定记录以后表格仍须显示未知。公开失败历史没有下载器实例字段，不能仅凭 hash 将其归为某次选种下载的异常。
- 扩展现有缺字段场景。订阅、下载、整理的 `data: null` 不能当作成功空列表；未知订阅执行状态和季集不明的同媒体任务须在「需留意」里标明，不能猜测为等待或正常。
- 新增共享读取预算场景。一个订阅请求耗尽预算不能阻止下载、队列、失败历史或详情媒体库独立开始并保留成功结果；用 HTTP 入站屏障与取消信号核对，不缩短生产超时。
- 扩展现有完成持久化场景。已知非默认剧集组即使随后关闭或重启也不生成默认季集的完成记录；洗版到货不能当作洗版目标已全部达成。完成详情显示当时的起始集和范围，不借用后台后来修改的范围。
- 最近完成的分页、他人隔离、删掉请求后的陈旧详情与重启失效由原主场景扩展验证，不另建重复单测。

## 第 4 项实施前验收设计

2026-10-10 开始「缺集下载方案」。复用当前搜索结果、站点筛选和串行批量下载；生成与重新计算只读媒体库及季信息，不重新访问 PT 站点。建议仅采用同来源、媒体、类型及明确单季的非空可信集数，不把未知整包、描述推断、多季资源或未映射编排当成完整覆盖。

方案以当前起始集至季末为所需范围，使用确定性贪心建议，最多沿用批量上限 20 个资源。优先新增缺集覆盖量，同覆盖时优先无 H&R、少重复、已知且较小体积，最后沿用 MoviePilot 的结果优先级；不宣称全局最优或最小体积。明确展示剩余缺口、重复已有、方案内重叠、范围外集数、已知大小与未知项，以及 H&R 和无做种风险。下载的是整个资源，不裁剪已有文件，也不保证站点资源最终可用。

## 第 5 项实施前验收设计

本轮实现单订阅立即搜索与执行跟踪，复用订阅详情、当前屏幕确认票据和 `Reply.Follow`。搜索与停止均需明确确认，读取、返回、停止刷新和关闭页面不触发业务操作。不增加配置、Cookie 要求、后台服务或持久化字段；搜索回执只保留在当前会话中，重启不重放写入，也不从后台最近批次恢复控制权。

Context7 的资料指向 `v3` 主线，未完整给出提交响应字段。本轮另核对主人提供的 `v3.1.1` OpenAPI 和官方固定版本源码。单订阅 POST 也可能合并已有任务；仅 `single=true`、目标与新建数均为 1、合并数为 0、唯一批次 ID 一致的回执能建立本地发起记录。已有批次不接管。批次只读响应没有完整订阅 ID 列表，停止前必须重新核对本地发起记录、订阅复合身份与归属、批次 ID／创建时间、`manual` 来源、单订阅总数、当前订阅 ID 及可取消状态；信息不足就不提供停止操作。

官方取消接口只请求在下载副作用边界前停止，已提交的下载不会撤销，`success=true` 不等于已停止。暂停订阅也不会停止已经受理的搜索，手动搜索暂停中的订阅不会恢复其自动调度。界面明确区分这些行为；批次完成不证明找到资源、下载完成或媒体库可见。

## 第 6 项下载暂停与继续的实施安排

首版只增加任务详情中的单任务暂停与继续，复用当前白名单、会话确认、下载实例身份和只读刷新。限速、批量控制、自动暂停策略及订阅暂停联动不在首版范围，后续需要时分别核验和确认。

实现前核验最新稳定版的原生下载控制契约，固定支持的动作、下载器实例参数、任务状态与响应。核验通过后先扩展外部 fake 和 E2E，再实现一次写入与只读核对；若能力有缺口，按上节缩小功能或确定薄适配，不能默认实现新的下载控制引擎。

| 实施位置 | 改动边界 |
| --- | --- |
| `internal/moviepilot/`、`internal/flow/model.go` | 投影可信任务状态，提供带实例与 hash 的控制能力和安全结果；不改变创建、删除契约 |
| `internal/flow/tasks.go` 及相邻任务文件 | 按状态提供暂停或继续，显示当前实例对应的安全目标与动作，确认前重读身份，写前消费票据，回执只提供读取核对 |
| `internal/app/` | 仅在新增依赖确有必要时装配，沿用现有 HTTP client、logger 和 Backend 注入 |
| `e2e/` 与相关文档 | 真实 app 对 HTTP fake 验证新增行为缺口，每个主场景保存脱敏 transcript；同步操作说明与局部规则 |

实现前失败清单如下。已有会话隔离、陈旧按钮和通用投递安全场景继续复用，只有新控制路径穿过这些边界且存在覆盖缺口时才扩展。

| 主验收行为 | 可信失败方式 | 可重复核验的结果 |
| --- | --- | --- |
| 动作与确认 | 状态不支持、尚未确认、重复点击、旧确认或刷新后目标变化 | 暂停与继续分别确认，只对当前有效目标写一次；停止刷新、停止后续提交与删除入口保持不同含义 |
| 实例与身份 | 同 hash 多实例、实例缺失、目标已消失或被替换、写前读取失败 | 始终绑定实例与 hash，不回退默认实例，不对错误目标发写请求；只读详情仍可核对 |
| 结果与失败 | 认证拒绝、HTTP 200 业务拒绝、缺字段、敏感错误、重定向、超时或响应丢失 | 明确拒绝与未知结果分开，不跟随写入跳转、不自动重试；回执和后续刷新不把受理当最终状态 |
| 并发与生命周期 | 后台状态同时变化、投递失败、应用退出或重启 | 客户端预检只证明读取时身份；只恢复展示，重启不重放控制操作，未确认的操作不写 |

本项成功标准是主人可在一个可信任务详情中显式确认暂停或继续，fake 能核对正确实例的一次控制请求，并在只读刷新中展示实际状态。无新增必需凭据、环境变量或服务。代码回退仅撤下控制入口，已修改的真实任务状态由主人核对和决定，不能通过回退自动反向操作。

## 第 7 项处理进度的实施前验收设计

2026-10-12 核验 MP 最新稳定版 `v3.1.4`（部署同版本）：

- 原生 `GET /api/v1/system/progress/{process_type}` 只接受资源 Cookie（`verify_resource_token`），每 0.5 秒推送一次 SSE。资源令牌 30 分钟过期，`RESOURCE_SECRET_KEY` 未固定时每次 MP 重启都会轮换，目标部署已按主人选择清除 Cookie，因此 Go 无法用 API key 稳定读取。这是认证可靠性缺口。
- `filetransfer` 键只有整个整理队列的「已处理 / 总数」，没有目标身份，不能归给单个任务。逐文件进度写在 `md5(Path(fileitem.path).as_posix())` 键下，复制、移动和上传网盘时上报（`app/modules/filemanager/storages/__init__.py` 的 `transfer_process`）；硬链接、软链接没有进度。官方网页整理队列对每个 `running` 任务订阅同一键，最多 12 个，只取 `enable` 与 `value`。
- 只读查询 `Directories` 的整理方式字段（未输出路径）：目标部署为本地移动到 OpenList（`alist` 上传），正属于有逐文件进度的慢路径。
- 公开插件 SDK 没有整理队列或进度入口，故 MP 侧 Crychic 插件增加内部适配：只读 `JobManager().list_jobs()`（`/transfer/queue` 的同一来源）与 `ProgressHelper`，经 API key 返回运行中文件的身份与 `{active, percent}`；不返回路径、文件名、进度文本或错误。键规则沿用宿主写入方，版本变化时由隔离宿主 E2E 复核。

Go 仅在整理任务有运行中文件时读一次插件进度，按媒体来源与 ID、季、集范围、下载 hash 与实例匹配；同一身份出现多次或插件不可用时保留原逐文件状态。整理完成仍不表示媒体服务器可见，下载、通知与订阅语义不变。

| 主验收行为 | 可信失败方式 | 可重复核验的结果 |
| --- | --- | --- |
| 进度归属 | 全局进度、同一身份多个运行文件、进度键残留、队列与进度快照之间状态变化 | 只给唯一匹配且仍在运行的文件加百分比，从不把全局或他人进度赋给任务 |
| 插件可用性 | 插件未安装或旧版本 404、停用、宿主结构变化、认证拒绝、超时、半响应 | 任务页照常显示逐文件状态，不提示失败，不影响下载与整理读取 |
| 隐私 | 路径、文件名、站点名进入进度文本或错误 | 插件投影只含身份与数值；Go 不记录或展示路径 |
| 生命周期 | 跟随刷新、停止刷新、任务结束 | 进度随跟随刷新读取，停止或结束后不再读取 |

宿主验证在官方 `v3.1.4` 镜像内用真实 `JobManager` 与 `ProgressHelper` 建立运行中任务和进度，经真实插件 HTTP 路由读取；Go 侧以真实 app 对 fake 验证匹配、歧义与插件缺失。插件需要主人更新到新版本后才在线上生效，未更新时保持现有行为。

- 插件自有数据库保存安全投影与独立进度，普通重启续接；Go 先原子保存投递尝试再发送，未知结果不重放。首次基线不广播旧记录。
- 首次切换时原本地到货、完成、停滞、静默合并、媒体库等待和周报退役，请求归属、权限和最近 50 条可信完成暂时保留；随后按多用户后置决策一并删除。旧文件有回退副本，旧 pending 和 digest 不补发。
- 复核 MP 3.1.4 调度源码时发现插件模块先于系统渠道执行，durable 通知的 strict 调度会传播插件异常。原实现的渠道歧义、缺默认目标、正文过长等错误会让其他原生渠道反复收不到这类通知；现改为捕获失败只停 Crychic 这一条并记录固定代码，长轮询与确认的数据库访问移出宿主事件循环。隔离宿主 E2E 增加对应场景。
- 2026-10-11 应主人要求，代理把插件放入 MP 本地插件仓库（`PLUGIN_LOCAL_REPO_PATHS`）；安装、启用插件及配置 crychic 渠道和受众由主人完成，随后部署新版机器人。首次启动的基线为第 0 条，请求记录迁移前后的数量一致。主人在机器人中订阅以触发 MP 原生通知，确认可正常收到；三条通知均已消费，两侧都没有错误日志；重启机器人后从原进度续接，没有重发。线上只配置了 crychic 一条通知渠道，所以「不影响其他原生渠道」只由隔离宿主 E2E 覆盖。代理未访问真实资源搜索，也未调用订阅或下载写接口。插件说明见 [README](../../plugins.v3/crychic/README.md)，失败清单见 [E2E 设计](../../e2e/native_notifications_design.md)。

### 接入方式与切换条件

原先优先评估 `GET /api/v1/message/notification` 的安排由插件接入方向替代，不将通知历史直接当作渠道实际投递来源，也不以 Telegram Bot API 网关作为默认方案。插件只补足通知接入能力，常规功能继续使用原生 API。不新增必需账户、资源 Cookie、消息中间件或第二套通知业务配置系统。

```text
MoviePilot 原生通知与发送策略 -> MP 侧 Crychic 插件 -> Go 应用安全投影、样式与传输 -> Telegram
```

插件扩展不自动继承全部渠道行为。功能实施前必须核验最新稳定版的适用扩展点、渠道过滤、发送时段、受众路由和插件生命周期，再确定具体接入点、公共接口及传输协议；目标部署有明确版本差异时增加针对性验证。现有插件通过认证 status、notifications 长轮询及幂等 ack 提供传输，安装步骤见插件说明。

以下条件须通过源码核验与外部 HTTP fake 固定契约。

1. 接出的消息确实属于需要投递的 MP 通知；保留类型开关、发送时段和受众语义，不因监听某个事件就直接发送。
2. 能取得稳定的消息身份、可信传输顺序与接收范围，不依赖解析标题或正文猜测归属，也不将相同正文当作可靠去重身份。
3. 仅接管明确选定的通知目标，不全局阻断其他原生渠道，避免未经说明的重复投递；切换不自动修改 MP 的渠道或用户绑定。
4. 插件停用、连接中断或不兼容时安全停止通知接入，不自动改用历史轮询、共享系统 SSE 或本地通知业务规则。

接入点不能满足上述条件时停止实施并报告具体差异，不在插件或 Go 应用中重写 MP 的过滤、时段或用户路由来冒充行为一致。插件缺口与核验结论须随功能交付记录；实现采用原生自定义 crychic 渠道与公开模块扩展，窄范围适配复用宿主检查及可信 durable 事件身份。

`GET /api/v1/system/message` 不作为替代来源。其共享内存队列会被消费，网页与机器人可能竞争，且没有独立消费者的可靠重放能力。`POST /api/v1/message/` 和 `/api/v1/webhook/` 是接收外部消息的入口，也不作为对外通知订阅或代发接口。

原历史 API 方案的核验依据保留为项目的 `v3.1.1` OpenAPI，以及官方 `v3.1.1`、`v3.1.3` 的[通知历史接口](https://github.com/jxxghp/MoviePilot/blob/v3.1.3/app/api/endpoints/message.py)、[通知渠道管理](https://github.com/jxxghp/MoviePilot/blob/v3.1.3/app/api/endpoints/notification.py)、[消息模型](https://github.com/jxxghp/MoviePilot/blob/v3.1.3/app/schemas/message.py)和[实时消息队列](https://github.com/jxxghp/MoviePilot/blob/v3.1.3/app/application/messaging/message.py#L1215-L1338)。这些历史来源不作为新插件接入点已验证的证据。Context7 返回的是 `v3` 主线资料，不能据此宣称目标部署的通知行为已验证。

### 首次实施的请求记录与配置迁移（历史）

以下是首次通知切换时的迁移安排。请求保留部分后来退役；旧文件只留回退材料，当前不执行这些请求迁移步骤。`CRYCHIC_NOTIFY_INTERVAL` 当前只控制原生通知接入失败后的重试，其他旧业务变量只给迁移提示，详见 [通知参考](../agent-reference/notifications.md#旧状态与迁移)。

- 将请求归属与通知投递解耦。保留 `/requests`、订阅操作权限、已有最近完成记录和基于可靠 MP 事实的只读进度核对；这些功能不得再生成通知，也不从通知正文反推个人请求或虚构完成历史。
- 新通知使用独立的最小传输状态，不复用整理历史游标。首次接入建立基线，不广播 MP 旧通知；首次无通知也保存初始化状态。普通重启继续使用已保存的消息身份，接收失败或传输范围不完整不提交新的 checkpoint。
- 保留原 `requests.json` 中的请求归属与完成记录。旧通知专用的 pending、digest 和游标保留可回退材料，但不转成新通知补发；迁移失败不覆盖旧状态，不访问真实状态文件做试验。
- 退役 `CRYCHIC_NOTIFY_QUIET`、`CRYCHIC_NOTIFY_LIBRARY_WAIT`、`CRYCHIC_NOTIFY_STALL`、`CRYCHIC_NOTIFY_DIGEST` 的业务控制作用。旧部署显式配置这些变量时给出不含配置值的迁移提示，不自动改写 MP 设置。若读取式接入继续复用 `CRYCHIC_NOTIFY_INTERVAL`，它只控制读取频率，不能充当 MP 的发送时段。
- 目的地变化必须明确说明并保持受众隔离；空目的地不擅自解释为全员广播。MP 接收范围无法映射到现有 Telegram 目的地时，作为切换未满足条件处理。
- 保留先原子保存投递状态、再发送的取舍，发送结果未知不自动重放。Go 投递状态只保存身份和进度；MP 插件的持久队列保存展示所需安全投影，不保存原始 Message、未知附件、凭据或敏感路径。

首次实施按超过 8 个文件规划，范围包括 MP 侧 Crychic 插件与 Go 应用之间的通知接入和安全投影、`internal/notify/` 的通知替换和请求记录解耦、`internal/flow/` 的请求记录消费与回执文案、`internal/telegram/` 的展示与投递、`internal/app/` 的装配、`internal/config/` 的配置迁移，以及 `e2e/`、README、compose 示例和相关参考文档。现有插件位于 `plugins.v3/crychic/`，接口与安装说明已随功能交付；本轮计划更新不新增运行依赖。

## Cookie 认证方案

### 配置与凭据边界

已新增可选配置 `CRYCHIC_MOVIEPILOT_COOKIE`，内容仅为名为 `MoviePilot` 的资源 Cookie 值，不接受整段浏览器 Cookie 头或 `Set-Cookie` 内容。使用与回退说明见 [README](../../README.md#可选资源-cookie)。

- 未配置时保持现有 API key JSON 行为，不要求每位用户或现有部署重新设置账户。
- Cookie 由部署者通过受控环境注入；不在聊天中索取，不写进计划、compose 实值、日志、transcript 或 `requests.json`。
- 仅保留于进程内存，验证失败的错误信息不回显配置值。拒绝换行、额外 Cookie 项等不符合单值契约的输入。
- Cookie 只发送给已配置 MoviePilot 源站和明确允许的 SSE 路径；不发给 Telegram、海报服务、Bangumi 或跳转后的其他源站，不使用跨服务共享 Cookie jar。
- 复用现有 transport 和依赖注入，不改变 TLS 校验，不新增明文公网凭据传输。
- API key 与资源 Cookie 各司其职。不能把 API key 或普通登录 JWT 直接改名为 `MoviePilot` Cookie。

v3.1.1 源码校验 Cookie 的资源令牌用途及身份。`verify_token` 的 Bearer 分支维护资源 Cookie，API key 分支只校验身份，不负责签发或刷新资源 Cookie。[认证源码](https://github.com/jxxghp/MoviePilot/blob/v3.1.1/app/adapters/web/security/access.py#L176-L301)

### 过期和降级

- 资源 Cookie 可能过期或被撤销。首版不存账户密码、不实现自动登录或续期；由部署者安全更新有效 Cookie 并重启。
- SSE 认证失败时显示安全的不可用提示，普通元数据、订阅和任务 JSON 读取仍可使用 API key。
- 未配置 Cookie 时，在发起搜索前直接选择原 JSON 路径。
- 已发出的 SSE 搜索无论认证失败、断线、超时还是协议异常，都不自动重连或自动改发 JSON 搜索。用户显式选择重新搜索时才发起新的站点搜索，并说明可能重复访问站点。
- 纯进度快照读取失败可以回到现有 JSON 状态读取；不得因此重新执行搜索、订阅、下载或整理。

该设计依赖部署者能够提供目标 MoviePilot 接受的有效资源 Cookie。此前提不成立时，保留完整的 API key JSON 功能，禁用流式增强，不放宽鉴权。

## 流式资源搜索的行为约束

### 消费与展示

1. 同一次搜索代次只启动一次上游搜索；后台消费 SSE，前台沿用 `Reply.Follow` 获取只读快照。
2. 以 SSE 完整帧解析数据，不假设一次网络读取就是一个事件；处理心跳、错误、`append`、`replace` 和最终替换的分批信息。
3. 上游会将大型最终 `replace` 拆成首个 `replace` 加后续 `append`，并携带 `replace_batch`、`batch_index`、`batch_count`。中途断流不能当成完整结果。
4. 资源原始记录仍仅在内存保留并按现有下载契约回传。除现有不可展示的 `Torrent.Record` 外，仅向业务层投影安全字段；不记录原始 SSE 帧。
5. 每次搜索使用独立代次，资源使用会话内稳定身份。排序、筛选、去重和最终替换不能让旧编号指向另一资源。
6. 可以浏览已返回结果，但始终标明搜索未完成。进入资源详情后固定已选目标；新事件不能覆盖详情、确认页或成功回执。
7. 最终结果移除或改变了已选目标时，拒绝旧确认并要求重新选择，不能把其他候选偷偷替换成下载目标。
8. 后台消费与消息刷新分离，复用 `CRYCHIC_PROGRESS_INTERVAL`，当前默认值为 `5s`；首屏和终态及时投递，不逐事件刷屏。
9. Telegram 临时投递失败只重试同一展示结果，不重跑业务或站点搜索。旧搜索的迟到事件不得覆盖新搜索或已接受的导航。
10. 沿用现有资源搜索总预算；取消、会话结束与应用退出均关闭流并等待 worker 退出。取消本地等待不能宣称上游每个站点请求已即时停止。

最终排序和局部筛选继续使用现有规则，不以到达顺序替代 MoviePilot 优先级。`/api/v1/search/last` 不提供 Crychic 会话隔离，不能用来恢复本用户的搜索。

[搜索流与批处理源码](https://github.com/jxxghp/MoviePilot/blob/v3.1.1/app/api/endpoints/search.py#L97-L447)

## 处理进度与实时消息的取舍

第 7 项已按下文实施记录交付：原生进度流只认资源 Cookie，改由插件以 API key 投影运行文件的原生进度。以下为实施前的取舍记录。

`GET /api/v1/system/progress/{process_type}` 按处理类型返回当前进度快照。只允许在身份信息足以关联目标时显示细粒度进度；无法关联时保留原逐文件状态或明确标注为全局处理信息。不能把全局百分比赋给每个任务，也不能把整理完成当成媒体服务器已可见。[进度源码](https://github.com/jxxghp/MoviePilot/blob/v3.1.1/app/api/endpoints/system.py#L630-L664)

`GET /api/v1/system/message` 暂不接入常驻消费，也不提供人工连接真实服务的验证步骤。当前接口会取走共享队列里的消息，网页和机器人可能竞争；`role` 不隔离消费者，队列满时丢弃旧消息，没有可供本项目使用的可靠重放游标。

只有上游提供独立消费者、事件身份及断线重放能力后，才重新评估系统消息流。第 6 项前置的原生通知接入不以消费该流实现；通知范围按该前置任务的 MP 语义与受众核验条件执行。第 7 项若缺目标上下文，评估薄插件补足或保留现有读取，不恢复个人请求页，不从全局消息流推断任务身份。[消息路由](https://github.com/jxxghp/MoviePilot/blob/v3.1.1/app/api/endpoints/system.py#L711-L750) · [队列语义](https://github.com/jxxghp/MoviePilot/blob/v3.1.1/app/application/messaging/message.py#L1297-L1338)

## 其他功能的实施边界

- **订阅设置**：优先选择已有规则组；更新只提交明确改动字段，不覆盖其他后台设置。沿用订阅来源、媒体 ID、类型、季、剧集组和原创建时间预检。调整范围不能把未取得的集数当成已取得；写结果未知只刷新核对。
- **权限与异常展示**：不恢复 `/requests`、本地请求归属和最近完成。白名单内用户同等管理全部业务资源；目标可可靠关联时只展示 MP 结构化状态的安全摘要。未知值显示未知，不解析错误原文猜原因，不为异常提示另建后台历史轮询或自动修复。
- **补集方案**：仅对可信覆盖范围生成建议，明确重叠、重复已有、总大小与 H&R；不确定范围留给人工选择。最终使用现有确认和串行逐项提交，不自动下载。
- **立即搜索**：与只读刷新明确分开，确认时说明会访问站点且可能自动下载。只跟踪当前会话确认新建的单订阅批次，不接管后台合并批次；该安全范围不作为订阅归属规则。返回批次信息不足以确认控制范围时，不提供取消入口。停止不撤销已提交下载。
- **下载控制**：始终带下载器实例和 hash；暂停、继续、停止刷新、停止后续提交和删除分别命名。若扩展限速，每次明确确认目标与改动；按返回的每个动作结果展示，不把部分成功写成全部成功。
- **发现与剧集组**：保留 TMDB、Douban、Bangumi 来源身份。歧义让用户选择；剧集组变更需要媒体库、资源范围与日历映射一致，通知沿用 MP 对该编排的原生处理，不能只换页面上的季号或在 Go 端重算通知集数。
- **同系列和历史**：媒体库读取失败显示未知；合集勾选后逐项确认范围。历史分页从上游继续读取，不用扩大一个固定首屏冒充完整历史。
- **字幕**：保存由 MoviePilot 执行，目标与字幕均需确认；服务器路径不进消息。字幕下载不承诺自动校时、版本同步或已正确挂载到所有文件。

## 实现前的失败方式与端到端验收

先按下表枚举外部系统失败方式，再扩展 fake 和实现相应功能。只补真实行为缺口，不新增内部 mock、单元测试或变更侦测测试。已有安全行为由现有场景覆盖，只有新增交互缺口才增加场景。

| 范围 | 必须覆盖的失败方式与边界 | 可核验结果 |
| --- | --- | --- |
| Cookie | 未配置、格式错误、过期、撤销、跨源重定向、图片请求串用凭据 | JSON 原功能保留；不泄漏值；其他外部 fake 收不到 Cookie；不重复发起搜索 |
| SSE | 分片、心跳、空结果、重复候选、`append`、`replace` 分批、中断、错误帧、超时、无完整终态 | 有结果时可提前显示；不完整结果明确标记；旧编号不换目标；上游请求次数可核对 |
| 会话并发 | 搜索中选资源或导航、迟到事件、连点确认、他人点击、跨话题、退出与重启 | 原消息与目标不被错误覆盖；写入至多一次；旧 worker 不跨重启继续工作 |
| 消息投递 | 限流、编辑失败、响应迟到、结果未知 | 只恢复展示，不重跑业务；终态不被旧进度覆盖 |
| 订阅编辑与补搜 | 身份复用、权限不足、并发修改、明确拒绝、写结果未知、取消范围不明 | 不越权、不覆盖未修改设置、不自动重试写入或误停全局批次 |
| 权限与状态核对 | 未在白名单、目标身份缺失、状态未知、敏感错误、文件路径、订阅已结束但尚未入库 | 白名单内同等管理全部业务资源，会话仍隔离；只展示可靠关联的安全信息，不重建本地归属，不把搜索结束或订阅关闭当成到货 |
| 补集与下载控制 | 不连续集数、整包范围不明、已有库存、资源重叠、同 hash 不同实例、部分成功 | 覆盖范围不虚构；实例目标正确；确认与逐项回执保持一致 |
| 进度与通知 | 全局进度无法关联、流断开、整理完成但库不可见、插件停用或不兼容 | 进度保留原状态读取，不伪造单任务百分比；通知按第 6 项前置任务验收，不自行追加完成结论或推进错误游标；插件失效不影响原生 API 功能 |
| 发现与后续功能 | 跨来源重名、剧集组编号差异、旧历史翻页、系列部分查询失败、字幕目标不明 | 保留消歧和返回路径；不误订阅，不将未知当缺失 |

每个新增行为场景通过真实 app 连接 fake Telegram、fake MoviePilot 及所需的其他外部 fake，以 `h.tr.verify(t)` 结束。产物为经脱敏、可重复比对的 `e2e/testdata/transcripts/*.txt`，必要时增加合成 SSE fixture；认证只核对合成凭据，不记录真实 Cookie 或原始资源帧。

实施对应功能后执行：

```sh
go build ./cmd/crychic
go vet ./...
gofmt -l .
go test -race ./...
git diff --check
```

触及 MP 插件时另执行 `e2e/run_mp_plugin_e2e.sh`，普通运行比对已提交的宿主 transcript。仅文档更新按 [检查时机](../agent-reference/operations.md#检查时机) 检查文本、链接与 diff，不更新 golden，不为此运行真实机器人。

仅在交互行为有意变化时使用 `go test ./e2e/ -update`，逐行审阅 transcript 差异后同功能提交。失败或不可用的检查必须报告，不绕过检查提交。主人手测真实业务时核对提前出现结果、取消、Cookie 失效提示、目标稳定和最终操作结果；代理不代为执行。

## 发布与回退

- 按独立功能提交，计划保存不自动触发代码实施、部署或推送。
- 原生通知前置任务已完成，第 6 项直接复用当前部署，不再次迁移请求数据。通知回退保留独立游标及旧文件材料，不自动重放旧 pending、周报或发送结果未知的消息，不自动恢复或覆盖 MP 渠道配置。
- Cookie 与搜索流同一里程碑交付；移除 Cookie 配置即可在重启后恢复原 JSON 搜索。回退时不重放中断的搜索或未知写入。
- 进度流只增强显示，可以独立停止，原任务读取和通知链继续工作。新增插件能力按功能隔离，停用某能力不影响其余原生 API 功能。
- 订阅编辑、下载控制等已完成的外部变更不能由代码回退自动撤销；逐项回执与人工核对保留。
- 后续条目不新增本地请求归属、到货事实或完成历史。必要传输状态独立保存，兼容现有文件并原子写入，不重建或清空通知游标，也不删除旧请求文件。

## 2026-10-11 多用户后置决策记录

主人决定当前不做多用户，同时保留后续扩展的可能。MP v3.1.4 只有一个全局 `API_TOKEN`，并固定映射到超级用户，MP 无法区分聊天用户；本地请求归属只能在 Crychic 内模拟权限，维护成本高，还挡住了主人管理网页端创建的订阅。

已删除第 3 项「我的请求与异常」（`/requests` 与首页入口）、本地请求归属、到货事实与最近完成记录，以及只为它们服务的整理历史、失败历史和单订阅读取。订阅暂停、恢复、取消、条件编辑和立即搜索对白名单内用户全部开放，写前仍复核订阅复合身份。本文实施记录中关于请求归属、请求者权限和最近完成的内容保留为历史，不再代表当前行为。

多用户隔离等 MP 官方支持按用户的 API 凭据后再设计：按 `Actor` 选择凭据，归属沿用 MP 自身的用户体系，不重建本地归属表。当前约束见[用户与权限模型](../agent-reference/architecture.md#用户与权限模型)。
