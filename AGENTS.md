# Crychic

Go chat bot that searches media and creates subscriptions in MoviePilot (v3 API), or downloads a release picked from MoviePilot's resource search. Telegram ships; Discord is next. Scope: subscribe and download, whitelist auth.

## Commands

| Command | Description |
|---------|-------------|
| `go build ./cmd/crychic` | Build the binary |
| `go vet ./... && gofmt -l .` | Lint; both must print nothing |
| `go test -race ./...` | Run all tests (they live only in `e2e/`) |
| `go test ./e2e/ -run TestSubscribeMovie` | Run one scenario |
| `docker build -t crychic .` | Build the image (distroless, uid 65532, data at `/data`); `compose.example.yaml` shows a deployment |
| `go test ./e2e/ -update` | Regenerate golden transcripts after an intended behavior change |

## Architecture

```
cmd/crychic/         # main: config.Load(os.Getenv) → app.Run
internal/app/        # the only wiring point; shared by main and e2e
internal/flow/       # platform-agnostic conversation: search → pick (library check) → season → confirm → subscribe
internal/moviepilot/ # minimal MoviePilot client, implements flow.Backend
internal/bangumi/    # Bangumi's public API (no key): airing calendar and synopses, implements flow.Calendar
internal/telegram/   # renders flow.Reply as messages + inline keyboards; whitelist check; delivers notices
internal/notify/     # remembers requests (data dir JSON), polls MoviePilot transfer history, notifies requesters
internal/config/     # env vars → config.Config
e2e/                 # behavior tests: real app vs fake Telegram Bot API + fake MoviePilot + fake Bangumi
```

Arrivals: `notify.Notifier` polls `GET /api/v1/history/transfer` → `arrive` records matches as pending (media + season + episode range, plus one source file name per download, at most 3) → `flush` announces once settled → each download's quality is read from MoviePilot's own release-name recognizer (`GET /api/v1/media/recognize?title=<file>`, what its WebUI shows; also a TMDB lookup, ~2 s, cosmetic within 10 s, unrecognized answers `meta_info: null`) and shown once as small print, e.g. `1080p · BluRay · x265 · FLAC 2.0 · FROGE` → `telegram.Bot.Notify` posts in the requesting chat, mentioning the requester in groups. Only the file name of `src` is kept, never the server path.

With `CRYCHIC_TELEGRAM_NOTIFY_CHAT_ID` set, `notify.Options.Destination` replaces requester delivery: one notice per watch delivery to the channel, with no requester identity and no fallback to the originating chats. Blank keeps the original behavior. The destination is a negative chat ID or `@channelusername`; the bot needs channel posting rights. Delivery still persists before sending and does not replay failed sends.

Data flow: Telegram update → `telegram.adapter` → `flow.Engine.Start/Choose` → `flow.Backend` (MoviePilot) → `flow.Reply` → `sendRichMessage` (command) or `editMessageText` with `rich_message` (button) → `answerCallbackQuery` last.

## Key Files

- `internal/flow/model.go` - `Backend`, `Reply`, `UserError`: the contract every platform and backend uses; `conversation.go` defines the shared `Conversation` entry point used by chat adapters
- `internal/flow/engine.go` - conversation choices; `internal/flow/search.go` - ordinary searches retain all returned results, page 8 at a time, open unique results directly, and replace a query under a fresh session ID; `internal/flow/text.go` - result lines and media cards
- `internal/flow/recovery.go` - failed search, season and subscription reads keep their session and offer a read-only retry (`rt`); retry replaces the failed screen without adding a navigation step. Subscription writes go through `submit` once; transport/response failures or a missing positive ID point to `/subscribe`, never to a write retry
- `internal/flow/tasks.go` - `/tasks`: list downloads and transfer jobs, follow one live (`Reply.Follow`); `taskdelete.go`: a download's view offers 删除任务 (`kd`), which stops following, re-reads the download and asks, warning that its files go too and, when a subscription of the same media and season exists, that the subscription will not fetch it again; 确认删除 (`ky`) clears the download to confirm before the write, relays a refusal, points an unknown result to `/tasks`, and `Watcher.ForgetDownload`s it; `internal/telegram/follow.go` re-asks the flow every `CRYCHIC_PROGRESS_INTERVAL` and edits only on change
- `internal/flow/home.go` - `/start` home menu (`features`), typed title search; a feature with nothing to list (tasks, subscriptions, latest) only flashes a toast (`Reply.Notice`) and the menu stays, while the typed commands answer with a message; `internal/flow/charts.go` - `/trending` charts, paging, pick → subscribable result; 返回 on a pick redraws its chart page (retrying missing synopses). 取消 always ends the conversation
- `internal/flow/charts.go` calendar: 新番放送 opens on today's weekday (China time, `calendarZone`), one weekday per view with a 一…日 button row, picks sorted by first air date within the day
- `internal/flow/notes.go` - `/trending` calendar pages: each pick looked up on TMDB (title, then original title) for link + identity, synopsis from TMDB else Bangumi's own `/v0/subjects/{id}` (`flow.Calendar.Summary`, kept on `Media.CalendarID`); all three lookups of every pick on a page run at once (one round trip); a pick found with a synopsis is done for the session, one without is looked up again whenever its page shows (MoviePilot answers an upstream failure with an empty `MediaInfo`, HTTP 200, which is why synopses skip it). Other charts show the synopsis the chart carries (Douban's is a region / genre / director / cast line); chart and related entries are `Brief` (facts on the name's line, ` · ` apart); a chart entry with a synopsis opens by its name (`Block.Body`: synopsis, then 查看详情页 link), one without has its name linked
- `internal/flow/related.go` - 相似推荐 / 同系列 on a media card (season picker, movie confirm, held, already subscribed): lists related media or the movie's series like a chart (`pickEntry`, opening to synopses; generic `listPages` paging, which is a same-level step for 返回) with number buttons picking `actionMedia` directly; nothing found or a failed lookup only flashes a notice and keeps the card
- `internal/flow/nav.go` - 返回: every shown reply is kept with the session state behind it (`screen`); forward steps (`forward`: pick, season, 相似/系列, multi-season, start-episode prompt, chart pick, typed title) push the previous screen, same-level steps (paging, ticking, weekday, a typed episode) replace it, any other step clears the history; 返回 restores a screen exactly, with no backend call. `grid` lays out button rows
- `internal/flow/latest.go` - `/newly_added`: newest media server items linked to their web page
- `internal/flow/subs.go` - `/subscribe`: subscriptions one kind at a time (电视剧/电影 buttons, `sf`, same-level; TV first when there are any); number buttons open read-only details (`sd`); one shared 取消订阅 (`sc`, only when the shown kind holds one the user requested, `Watcher.Requested`) lists just those to pick and confirm, then `Watcher.Forget`
- `internal/flow/subdetail.go`, `subdetailtext.go`, `subprogress.go` - subscription details re-read the subscription list on open and 刷新 (`su`, same-level), keeping its original page for 返回. Settings and last-search execution state come from that list; library, downloads and transfer queue are read concurrently within the cosmetic budget. Exact kind + media identity + season associates tasks (movie and TV IDs can collide); unknown season/episode tasks only add a note. Library visibility is independent of task completion; a download percentage describes the whole torrent, not each file. Consecutive equal episode rows merge; at most 100 requested episodes, 20 table rows a page with explicit omissions. No resource names, sites, downloaders or file paths
- `internal/flow/history.go` - 订阅历史 (`hs` from the subscription list, `hf` switches kind): the kind's newest 10 past subscriptions (`GET /api/v1/subscribe/history/{电视剧|电影}?page=1&count=10`); a pick (`hp`) already subscribed only flashes a notice (lookup failure still asks), otherwise a card asks; 确认重新订阅 (`ho`) posts the history record back unchanged like MoviePilot's WebUI (MoviePilot drops its id/state fields and keeps its settings), then watches for arrivals like any request
- `internal/flow/torrents.go`, `torrenttext.go` - 搜索资源 on a card with a chosen target (movie confirm, held, already subscribed, a season's start-episode prompt; `session.focus`): `ts`/`tr` start the slow site search in the background (`torrenthunt.go`, `session.hunt`; 取消 stops it) and show the card with a searching line and `Reply.Follow` (`tg` leads on from the card, `tq` replaces a failure): each refresh only checks the search, saying how many seconds it has run (from `Now`, so `h.advance` moves it) until the results replace it; releases list in MoviePilot's order (8 a page, number buttons `tp` carrying each release's own index), re-sortable like the WebUI (`torrentsort.go`: 默认/做种/时间/大小/站点, `to`, same-level) and filtered to one site (筛选站点 `tf` lists sites with counts, `tw` picks one or all; its 返回 re-shows the list), all in the session without searching again, a pick shows the release under the card (two tables, H&R warning) and 确认下载 (`td`) writes once (the release to confirm is cleared before the write; a refusal is relayed, an unknown result points to `/tasks`, never a retry), then watches the download by its id for arrivals; `torrentbatch.go`: 多选… (`tm`, forward) turns the number buttons into ticks (`tk`, same-level, stays on the ticked one's page, at most `maxTickedReleases`) kept across paging, sort and site filter; 下载所选 N 个 (`tb`) lists the ticked releases under the card and 确认下载 (`tz`) clears the batch before writing each once, tabling each release's outcome (refusal relayed, unknown → `/tasks`); every started download gets its own watch, so each arrives as its own notice
- `internal/flow/seasons.go` - multi-season picker (「多选季…」): tick seasons, subscribe each from episode 1, report per season
- `internal/flow/episodes.go` - start-episode choices for seasons and typed answers (`Engine.Answer`)
- `internal/flow/rich.go` - `flow.Text`: blocks by meaning (`Heading`, `Line` paragraphs, numbered `entry` items (a `Body` folds behind the name), `Group` section heads, `Quote`, `Table` (columns empty in every row are dropped), `Ticked` checklist lines, `Open` link button, `Small` print, `Remark` notes, `Divider`) of spans (bold, italic, code, link); an entry's `Tag` is a highlighted fact (你请求的)
- `internal/telegram/rich.go` - renders `flow.Text` as a Telegram rich message (Bot API 10.1 rich HTML: `h3`/`h4`, `p` with `br`, `ol`/`li value`, `blockquote expandable` (card synopsis), `li` > `details`/`summary` (an entry with a body; closed by default, the summary keeps name and facts), `table bordered compact`, `ul` with `input type=checkbox`, `mark`, `tg-button-row`/`tg-button type=url`, `tg-slideshow` (gallery), `footer` (remarks, and `Small` print mid-message: rich HTML has no font size below headings, and the owner chose a footer over `h6`/`sub` on a live sample), `hr`, `img`), escaping everything
- `internal/telegram/posters.go` - remembers every shown poster's file_id and sends it by file_id next time; downloads and uploads posters Telegram cannot fetch itself (hotlinked hosts)
- `internal/telegram/home.go` - sends and edits every reply as a rich message; `/start` shows the embedded `assets/home.jpg` as the message's media (uploaded once, then by file_id), so home and the features it opens share one message; only the home menu carries it (the owner dropped per-feature banners). A home photo sent by an earlier version is replaced by a new message, then deleted
- `internal/flow/store.go` - in-memory sessions (10 min TTL)
- `internal/flow/pages.go` - bounded pages for subscriptions, tasks and latest items; page buttons keep item indices stable
- `internal/telegram/lanes.go` - serializes each message's state transition and edit, including background refreshes
- `internal/notify/state.go` - pure state transitions (`withRequest`, `arrive`, `flush`, `withActivity`) and atomic persistence
- `e2e/harness_test.go` - `start`, `say`, `answer`, `answerQuoting`, `chatter`, `tap`, `tapData`, `shows`, `arrives`, `transfers`, `reports`, `restart`
- `e2e/testdata/transcripts/*.txt` - golden transcripts, one per scenario

## Environment

- `CRYCHIC_MOVIEPILOT_URL`, `CRYCHIC_MOVIEPILOT_API_KEY` (MoviePilot `API_TOKEN`), `CRYCHIC_TELEGRAM_TOKEN` - required
- `CRYCHIC_TELEGRAM_ALLOWED_USERS` - required, comma-separated user IDs; empty refuses to start
- `CRYCHIC_TELEGRAM_API_URL` - optional, defaults to `https://api.telegram.org`
- `CRYCHIC_TELEGRAM_NOTIFY_CHAT_ID` - optional arrival channel, negative ID or `@channelusername`; empty notifies request chats
- `CRYCHIC_BANGUMI_API_URL` - optional, defaults to `https://api.bgm.tv`; the 新番放送 calendar is read from it
- `CRYCHIC_DATA_DIR` - optional, defaults to `data`; holds `requests.json` (pending requests, last seen transfer)
- `CRYCHIC_NOTIFY_INTERVAL` - optional, defaults to `1m`, minimum `100ms`; how often transfer history is polled
- `CRYCHIC_NOTIFY_LIBRARY_WAIT` - optional, defaults to `30m`, `0s` disables; how long a settled notice waits for the media server to show the arrival
- `CRYCHIC_PROGRESS_INTERVAL` - optional, defaults to `5s`, minimum `100ms`; how often a followed `/tasks` view refreshes (Telegram throttles frequent edits)
- `CRYCHIC_NOTIFY_STALL` - optional, defaults to `6h`, `0s` disables; how long a requested download may make no progress before its requesters (or the notify channel) are told once that it seems stuck
- `CRYCHIC_NOTIFY_QUIET` - optional, defaults to `3m`, `0s` disables; how long a show's arrivals settle before one notice covers them

## Code Style

- `flow` must never import a platform package; a new platform is a sibling of `internal/telegram` that consumes `flow` through a small interface
- Inject dependencies (`Backend`, `Now`, `*http.Client`, `*slog.Logger`); construct concrete types only in `internal/app`
- Buttons only choose (the one exception is a notice's `flow.Open` link, e.g. 在 Emby 中观看): no emoji, no titles or facts in labels. Picks are number buttons (`gridColumns` a row) or short names (第 N 季), with the details in the message text; menus share rows (`menuColumns`)
- Button rows run in one order: choices (numbers and their pager, seasons, 确认X on a row of its own), switches (电视剧/电影, weekdays; the shown one marked `·X·` by `markShown`), onward actions (搜索资源/相似推荐/同系列 via `onward`, 订阅历史, 重新搜索 on its own row), and last the one navigation row
- Navigation has one vocabulary. A request (search, subscribe, download, resubscribe) ends with 取消; a browsing screen (lists, details, charts, task views) ends with `browseRow`: 首页 then 关闭 (`c`, generic). Every way back is labelled 返回 (`labelBack`): navigate's history (`bk`, put in front of 取消/首页/关闭 by `withBack`) or `backTo` a list read afresh (tasks `l`, subscriptions `j`, history `hf`, charts `b`); a screen never shows two. Destructive confirmations are 确认X over 返回 alone
- Data with columns (season picker, multi-season results, a task's files or progress) is a `flow.Table`; the multi-season picker shows its ticks as `Ticked` lines
- Numbered list entries are `flow.entry` (an `Item` block): bold name, then facts (original title, year, kind, rating, state, progress) in italics below it, rendered as `<li value="n">` so numbers match the buttons on every page. Each message opens with a `Heading`; list sections and calendar dates are `Group`s, page numbers and refresh state are `Remark`s (footer), a media card's original title, year / kind / rating, genres / length and cast share one line of `Small` print (joined by ` · `) under its heading, and a media card is separated from its question by a `Divider`
- User-facing copy is `flow.Text` built with `Strong`/`Emphasis`/`Mono`/`Linked`/`Quote`; never put platform markup in flow strings, adapters render and escape. Emoji sparingly: 🔍 search, 🎬/📺 card, ✅ done, ℹ️ already subscribed, ⬇️/⏸️ download progress, 📦 transfer job (⏳ ▶️ ✅ ⚠️ per file), 📋 task list, 📥 arrival, ⚠️ errors, ⌛ expired, 🚫 refused
- Voice: the bot is cheerful and cute, calls itself 我 and the user 你, ends sentences with 啦/哦/呀/～. At most one kaomoji per message, only on home, success, empty/failed results and arrival notices (never in headings, toasts, tables or facts), from this set: `(๑•̀ㅂ•́)و✧` `ヾ(≧▽≦*)o` `(ﾉ>ω<)ﾉ` `(｡•́︿•̀｡)` `(´-ω-`)`. Data stays neutral (titles, facts, table heads, subscription states, 第 N 季, page numbers, file states, chart names, the 你请求的 tag), as do button labels and the command menu. Safety meaning never softens: an unknown subscription result still sends the user to `/subscribe` first, cancelling still says MoviePilot stops downloading, an API key refusal still names the admin; MoviePilot's own refusal messages are relayed verbatim
- Errors safe to show users are `*flow.UserError`; others get logged and shown as the generic outage text
- Hard limits: functions ≤ 50 lines, nesting ≤ 3, ≤ 3 positional params (use a struct, e.g. `moviepilot.call`), complexity ≤ 10, no magic numbers

## Testing

- **Agents never write to a real MoviePilot**: no `POST /api/v1/subscribe/`, no `POST`/`DELETE /api/v1/download/`, no resource searches (`/api/v1/search/*` queries the owner's PT sites) and no bot runs that end in a subscription or download. A real subscription makes MoviePilot search and download from the owner's PT sites and can get the account banned. Agents' live calls are limited to read-only metadata endpoints; write paths are verified through the fakes and MoviePilot's source. The owner may test the live bot by hand
- `transcript.verify` also fails any message the bot sends or edits whose content (posters aside) does not open with a `<h3>` heading: every message, endings, expiries and empty states included, opens with a `Heading` (`titled` adds one to a bare failure)
- End-to-end only: no unit tests, no mocks of internal packages, no redundant or change-detection tests
- Every scenario ends with `h.tr.verify(t)`; after `-update`, review the transcript diff line by line and commit it with the code
- Press buttons with `tap(user, msgID, label)` so a button missing from screen fails; use `tapData` only for deliberately stale buttons
- The fake MoviePilot answers the library and downloader checks as an idle server (`idleServer`); scenarios override `libraryShowPath`/`libraryMoviePath`/`downloadsPath`. `DELETE /api/v1/download/{hash}` succeeds for a hash in the current download list, which then leaves it; a route for the exact path overrides that
- Recordings of `/api/v1/download/` carry tracker URLs with passkeys, the site name, the release name and the owner's username: keep only the fields Crychic reads
- Fakes must behave like the real services (long-poll `getUpdates`, `X-API-KEY` check, real error shapes); extend them, don't shortcut them
- The fake Telegram accepts only `sendRichMessage` and rich `editMessageText`, refuses rich HTML with undocumented tags or unbalanced markup, and records each message's HTML a block or `<br>` per transcript line. `h.tg.refuseImage(url)` fails media blocks with that URL; `h.tg.seedPhoto` leaves a pre-rich-message photo menu in a chat
- `fakeImages` is Douban's image host: 418 without the Douban referer, 403 to Go's default User-Agent, a tiny JPEG per path otherwise, `h.img.setMissing(path)` answers 404; `app.Deps.Images` routes poster downloads to it. The fake Telegram hands out a file_id per upload, returns the top photo or slideshow with file_ids, accepts known file_ids only, and records uploads as `photo=` and reuses as `reuses=`
- `e2e/testdata/bangumi/calendar.json` is a trimmed recording of `api.bgm.tv/calendar` (all seven weekday groups, a few shows, only fields Crychic reads); `subject_<id>.json` record `/v0/subjects/<id>` the same way and `not_found.json` is Bangumi's live 404. `h.bgm.setDown(id, true)` makes a subject answer 503. Scenarios start on `epoch`, Monday 2026-10-05 noon China time, and the clock runs at real speed from there (`app.Deps.Now`), so "today" is stable; `h.advance` adds an atomic clock offset for expiry scenarios without changing real timer cadence
- `e2e/testdata/moviepilot/*.json` are trimmed recordings from a live v3.1.0 instance (`curl -H "X-API-KEY: $KEY" "$MP/api/v1/media/search?title=沙丘&type=media&count=10"`), except `subscribe_rejected.json`, `server_error.json`, `library_movie_held.json` (the live library holds no movie yet), `subscriptions.json`, `subscribe_deleted.json` (no live subscription may be created to record them; `subscriptions.json` copies the shape of recorded subscription history); `latest.json` is a live recording with the owner's Emby domain replaced by `emby.example.com`; `subscribe_created.json` came from a one-off live subscription that must not be repeated (see above); `torrents_*.json`, `download_*.json`, `downloads_dune_mygo.json` are synthetic, shaped after v3.1.0's `Context.to_dict()` and download endpoint, with a fake site cookie and passkey the fake checks come back in `POST /api/v1/download/` (recorded as a summary) and scenarios check never reach a chat; never commit real keys or tokens

## Gotchas

- The API key authenticates as MoviePilot's **superuser**; every subscription is owned by the admin, not the chat user
- Media `type` is a Chinese enum: `电影`, `电视剧`; results without `media_source`/`media_id` are dropped
- Every JSON endpoint answers `{success, message, data}`, even where the route's `response_model` says `List[...]` (wrapped by `app/api/response.py`); `moviepilot.Client.do` unwraps it, and `success: false` on HTTP 200 becomes a `UserError` with `message`
- `GET /api/v1/subscribe/media/{id}` returns `data` with `id: null` when nothing is subscribed, not a 404
- Every message is a rich message (`sendRichMessage`; edits pass `rich_message`, and the library's empty `text` field is accepted). Media posters are an `<img>` block on top; search result, chart, 相似推荐 and 同系列 pages carry their entries' posters as `Reply.Gallery`, a `<tg-slideshow>` on top in list order (Telegram shows no per-slide captions, so slides carry no text). Telegram fetches posters itself the first time; every poster's `file_id` is then read from Telegram's copy of the message and later messages send it by `file_id` (`tg://photo?id=pN` media, transcripts show `reuses=`), so Telegram need not fetch it again. A refused message forgets the file_ids it reused and is retried once with its posters sent afresh, then without any poster (Telegram does not say which one failed; not for "message is not modified"). Douban images (`*.doubanio.com`, all Douban charts and 正在热映) answer 418 without a Douban referer, so Telegram cannot fetch them: `internal/telegram/posters.go` downloads them with the referer and its own User-Agent (`img3` answers 403 to Go's default one; 5 s budget, 5 MB cap, 4 at a time), uploads them as `attach://` media (file_ids: memory only, LRU of 1000, gone on restart); a poster that fails to download is dropped alone. MoviePilot's WebUI shows them through its own image proxy (`/api/v1/system/img`), which Telegram cannot reach. Rich HTML collapses newlines, so the renderer turns them into `<br>`. The home menu alone sets `Reply.Banner` (`flow.BannerHome`; every name in `flow.Banners` needs a bundled JPEG or the bot stops at start); the banner goes through the poster file_id cache as `banner:<name>`, uploaded once and then reused like a poster. Empty feature buttons only flash a notice and leave the home banner untouched. Telegram clients often keep showing the old top image after an edit changes it until the chat is reopened; the bot's requests are right, and the owner chose not to work around it. Photo messages (home menus from before rich messages) cannot become rich text, so a press on one sends a new message and deletes the photo; photos are recognized from callback metadata; `Reply.Notice` keeps them untouched
- Poster URLs from MoviePilot are TMDB `original` size (MBs); `moviepilot` rewrites them to `w500` (`posterURL`)
- `GET /api/v1/media/{id}` details are cosmetic: on failure the card falls back to search metadata and the flow continues; its `directors` field mixes in producers and episode directors, so it isn't shown
- Subscriptions take `start_episode` (per season): MoviePilot skips earlier episodes. "只追新集" uses details' `next_episode_to_air` and only shows when it is in the chosen season and > 1; button data `ok:<n>` carries the start, validated against the season's episode count before the session is taken
- The bot registers its command menu (`setMyCommands`, `telegram.commands`) on every start, for the default scope and for each whitelisted user's chat (a chat-scoped menu outranks the default; the owner's token carried a stale one from an earlier program); keep it in step with `parseCommand`'s commands and `help`
- Typed answers: a `Reply` with `Input` makes the Telegram adapter remember (chat, user) → message in `adapter.pending`, including initial sends. Private chats take plain text as an answer while pending, otherwise search it as a title; `/start` and `/search` clear the old pending input. Private text/commands share an input lane so old answers cannot restore a cleared prompt. Groups only take a reply quoting the prompt
- Resource search is `GET /api/v1/search/media/{id}?media_source=&mtype=&season=` (MoviePilot searches every indexer site while the request waits, tens of seconds; `torrentSearchTimeout`), answering `Context.to_dict()` items; nothing found is `success: false`, 未搜索到任何资源. Their `torrent_info` carries the site's cookie, user agent and download link: `moviepilot` keeps `media_info` + `torrent_info` raw as `flow.Torrent.Record`, which is never shown, logged or persisted, and `POST /api/v1/download/` gets it back unchanged as `{media_in, torrent_in}` like the WebUI; the answer's `download_id` is the torrent hash. A download's watch (`Request.Download`, `watch.Download`) matches transfers by `download_hash` and its season, ends when its wanted episodes arrived (a release's episode range, else the season), or `orphanGrace` after the download left `GET /api/v1/download/`; stall notices match it by hash
- MoviePilot has no outgoing webhook, so arrivals come from polling transfer history (one record per file, newest first, `seasons` "S03", `episodes` "E01" or "E01-E03"). The first poll only records the latest id (baseline), so history from before Crychic is never announced
- MoviePilot closes a subscription when downloads finish, before files are transferred: a closed subscription must not end a watch. Watches end when every wanted episode arrived (movies: first arrival) or after `orphanGrace` (72h) with the subscription gone
- MoviePilot transfers episodes one by one as their downloads finish, often minutes apart. A show's arrivals stay pending (persisted) until nothing new came for `CRYCHIC_NOTIFY_QUIET`, then go out as one notice; a watch whose every wanted episode is in (and any movie) is announced at once. The e2e default is `300ms`; `transfers` waits until a whole poll handled the records, so a test can act between polls
- A settled notice is held until the media server shows the arrival (`exists_remote`/`notexists`; rclone/alist dir caches can delay Emby by minutes), at most `CRYCHIC_NOTIFY_LIBRARY_WAIT`; the notice then links to the item from `GET /api/v1/mediaserver/latest` (matched by title + year; `link` is the server's public web URL, item `image` is an internal URL and is not used). The fake media server shows every transfer on top of the scenario's library fixture; `scenario.lagging` + `h.catchUp` model a server that has not scanned yet. Library and latest reads are polled, so they stay out of transcripts
- The fake answers `recognize` per file name (`scenario.recognized`, others get `recognize_none.json` like live); fake transfers carry `Src`/`Hash` only where a scenario needs qualities
- Notifier state is saved before notices are sent: a crash may drop a notice, never repeat one. Polling calls are kept out of e2e transcripts; the notices they cause are recorded
- Button data is `<session>:<action>:<arg>` and must stay ≤ 64 bytes (Telegram limit). A stale button only has its action to go on, so `/tasks` buttons use their own actions (`k f u l c`) and `flow.expired` points them back to `/tasks`, everything else to `/search`
- The fake numbers subscriptions created from `subscribe_created.json` 1, 2, 3, ... like MoviePilot; two watches sharing an id would merge; it likewise answers each added download with its own hash (`addedHash`, then `addedHashN(n)`)
- Confirm and cancel use `store.take`, so a double tap acts once; keep that for any step that ends a conversation. 重新订阅 keeps its session for 返回 to the history: steps of a session run one at a time and it clears the confirmable target before writing, so a second tap only gets a notice. Failed reads clear the confirmable target but keep their context; only the failed read is repeated, and success clears retry state. Failed writes consume the session too, preserving a safe MoviePilot refusal or reporting an unknown result to check with `/subscribe`
- Unique ordinary search results open directly, but chart identity disambiguation still requires a pick. A sole season only skips the picker when its number is positive; specials are never selected implicitly. Both shortcuts keep final confirmation. `重新搜索` (`rs`) replaces the old session when the new title is submitted; empty results keep a typed-title prompt. Generic paging records its screen, so 返回 restores the page selected from
- Session IDs are random across restarts; never replace them with a counter that resets on startup. `Choose`/`Answer` validate both user and chat and serialize steps per session. Calendar annotations clone both mutable slices before writing. E2E transcripts normalize opaque session IDs only when recording, never in updates sent to the app
- Callback action strings are unique across every flow handler. Resource search is `ts`/`tg`/`tr`/`tq`, release pick `tp`, ticking releases `tm`/`tk`/`tb`/`tz`, release order `to`, site filter `tf`/`tw`, download `td`, download deletion `kd`/`ky`; subscription return is `j`, subscription kind `sf`, shared cancel `sc`, subscription details/refresh `sd`/`su`, history `hs`/`hf`/`hp`/`ho`, calendar weekday is `w`, generic list paging is `p`, 相似推荐 is `r`, 同系列 is `n`, 重新搜索 is `rs`, read-only 重试 is `rt` and 返回 is `bk`
- MoviePilot calls are bounded per call (`moviepilot.callTimeout`, 30 s; resource search `torrentSearchTimeout`, 2 min), so its `http.Client` sets no `Timeout`. A call whose body carries site credentials (`call.secret`, the download post) never quotes MoviePilot's error answer, which can echo the request. An owner's button press stops the message's follower before waiting for the message lane, so a slow refresh never holds the press
- Telegram non-poll requests have a 10-second deadline including response-body reads; `getUpdates` uses the HTTP client's 70-second timeout. Metadata card enrichment uses a 5-second cosmetic budget; independent read-only calls overlap (a show's seasons are read alongside its details and library state). The Telegram adapter counts running handlers and followers and `Bot.Run` waits for them after polling stops, since the library does not, subscription writes do not. All clients share one transport keeping 16 idle connections per host
- List pages budget text and item buttons together (up to 20 entries and 3000 content runes). Large transfer views show at most 100 file lines, retaining the full aggregate count and explicitly naming omitted files
- `LibraryWait=0` bypasses media-server checks. Movies and complete seasons start that wait immediately; incomplete seasons start after quiet. Unchanged notifier state is not rewritten; necessary writes remain serialized under the state lock
- A `Reply` with `Notice` must not edit the message (another group member tapping your buttons)
- Library checks go through MoviePilot to its media server and are cosmetic like details (failure does not block confirmation, but the card marks the library state unknown instead of claiming absence). Shows use `POST /api/v1/mediaserver/exists_remote` (`{"3":[1,2,...]}`, `{}` when absent; needs `title`+`year`, ids alone answer `{}`). Movies use `POST /api/v1/mediaserver/notexists` (`[]` = held), because `exists_remote` answers `{}` for movies either way. `GET /api/v1/mediaserver/exists` reads MoviePilot's own sync table, which is empty unless library sync runs, so it isn't used
- `GET /api/v1/download/` lists unfinished torrents; `media` (source, id, `season` "S01", `episode` "E10-E12" or "E02、E04-E05", parsed segment by segment without filling gaps) comes from MoviePilot's download history and is null for torrents added by hand; `progress` is a percentage, `size` the bytes of the files being downloaded (qBittorrent `total_size`; shown in `/tasks` as e.g. `17.5 GiB`), `state` is `downloading` or `paused`, `left_time` is Chinese text like `1时5分3秒` (empty while stalled). The card shows the chosen target's downloads, cosmetic like details
- `/tasks` follows a task by re-reading `GET /api/v1/download/` (by torrent hash) or `GET /api/v1/transfer/queue` (by media + season; tasks are `waiting`/`running`/`completed`/`failed`, each file covers `meta.begin_episode` through `meta.end_episode`, inclusive; a missing end means one episode). Byte progress of a transfer is only an SSE stream behind a browser cookie (`/system/progress/filetransfer`), so transfers show per-file states. A view stops when its task leaves the list, when its owner presses 停止刷新, or after `flow.FollowFor` (10 min); any button press on a followed message cancels its follower first. Every task view has 返回 (`l`), which re-reads both lists in the same session (a finished view keeps its session for that). Both lists are polled, so the fake keeps them out of transcripts and `reports` swaps their fixture
- `DELETE /api/v1/download/{hash}` always deletes the files too (`delete_file=True` in v3.1.0) and answers only `success` (false when the downloader had no such task). Deleting does not undo a subscription: its `note` recorded the episodes as obtained when the torrent was added, and nothing in MoviePilot's core listens for the deletion, so the subscription never fetches them again
- `GET /api/v1/subscribe/` lists all subscriptions for the superuser key (`state` N/R/P/S, `lack_episode`, `total_episode`); `DELETE /api/v1/subscribe/{id}` answers 404 for one already gone, which `Unsubscribe` treats as done. Deleting a subscription only reduces downloads; the bot's other live writes are subscribing (and resubscribing), downloading a picked release and deleting a download
- Subscription details show what applies where a subscription sets nothing: no quality/resolution/effect is 不限, and no `filter_groups` falls back to the global `SubscribeFilterRuleGroups` setting (`GET /api/v1/system/setting/SubscribeFilterRuleGroups`; the per-kind default subscription configs only seed new subscriptions). MoviePilot schedules no search per subscription (`execution_status.next_run_at` is null after a run), so 自动查找 reads its scheduler (`GET /api/v1/dashboard/schedule`, the WebUI's 后台服务): `subscribe_refresh` browses the sites' newest releases (`SUBSCRIBE_MODE`, every `SUBSCRIBE_RSS_INTERVAL` minutes) and `subscribe_search` only exists while `SUBSCRIBE_SEARCH` is on; `next_run` is Chinese text such as 19分钟, status 等待 or 正在运行. Both reads are cosmetic, inside the details' budget (`flow.SubscriptionUpkeep`); `schedule.json` and `subscribe_filter_groups.json` are trimmed live recordings
- Only the subscription list attaches `execution_status`; `GET /api/v1/subscribe/{id}` does not. `last_search` and execution `next_run_at` are UTC timestamps, displayed in China time; missing/unrecognized timestamps and states stay unknown. MoviePilot v3.1.0's execution-error projection only flattens/truncates text, so it can still contain paths or credentials: `moviepilot` passes only `HasError` to flow, never the original error. `subscriptions_details.json`, `downloads_subscription.json`, `queue_subscription.json` and `library_subscription.json` are synthetic v3.1.0-shaped e2e fixtures, including an intentionally private-looking error to prove it is not shown
- Chart picks (`/api/v1/recommend/*`) are search-shaped but Douban/Bangumi ones carry Douban/Bangumi ids, while transfer history only carries TMDB ids; a pick is therefore searched by title (its original title searched at the same time, used only when the title finds nothing) and only taken directly when the identity or a unique title+year+kind matches, else the user picks. Douban season titles like 「流人 第六季」 often find nothing right. MoviePilot's Bangumi calendar (`/api/v1/recommend/bangumi_calendar`) loses the weekday grouping and serves 30 items a page (Monday to Wednesday), so the bot reads `api.bgm.tv/calendar` itself (summaries there are always empty; synopses come from TMDB, else Bangumi's subject API directly). A TMDB twin keeps its pick's `Weekday` and air date. Fake routes are keyed by path, so a scenario needing two searches swaps `searchPath` with `h.mp.setRoute`, or answers per title with `scenario.searches`. Reads the bot makes at once (calendar lookups) arrive in any order, so the transcript sorts each run of consecutive reads of one route (`transcript.settle`; media searches and details count as one route, searches first)
- 相似推荐 reads `GET /api/v1/tmdb/recommend/{tmdbid}/{电影|电视剧}` (TMDB media only; `type_name` must be the Chinese enum, `movie` answers 未知错误); `/tmdb/similar` is not used, its picks are poor. MoviePilot's details leave `collection_id` null (it reads TMDB's `belongs_to_collection` under the wrong name and drops `tmdb_info`), so 同系列 searches collections (`/api/v1/media/search?type=collection`, items `type` 系列) by the movie's titles and their stems (沙丘2 → 沙丘, `Dune: Part Two` → `Dune`), searches every name at once, then opens up to 3 candidates per name at once (`/api/v1/tmdb/collection/{id}`), and takes the first listing the movie in name order (a failed read before it is the answer); a series named unlike its films (哈利·波特与魔法石) is not found. The fake answers collection searches per title (`collectionSearch(title)`, `[]` otherwise, like MoviePilot), and the transcript sorts them like other simultaneous reads
- MoviePilot counts episodes as obtained once their torrent is added and closes the subscription then; it never checks progress (`chain/subscribe/completion.py`), so a dead torrent would end in silence. Each poll also reads `GET /api/v1/download/`: a non-paused download of a watched media/season (and, when known, a still-missing episode) whose progress has not changed for `CRYCHIC_NOTIFY_STALL` is told about once (`internal/notify/stall.go`). Progress marks live in memory (a restart restarts the clocks, so no state write per poll); the told torrent hashes persist in the watch (`stalled`), so a restart never repeats a stall notice
- Held episodes never appear in transfer history, so a `Request` carries `Held` and the watch counts them as delivered; MoviePilot's subscriptions themselves only download missing episodes
- When MoviePilot behavior is unclear, read its source (`app/api/endpoints/{media,subscribe}.py`) instead of guessing
