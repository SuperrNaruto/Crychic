# Crychic

Go chat bot that searches media and creates subscriptions in MoviePilot (v3 API), or downloads a release picked from MoviePilot's resource search. Telegram ships; Discord is next. Scope: subscribe and download, whitelist auth.

## Commands

| Command | Description |
|---------|-------------|
| `go build ./cmd/crychic` | Build the binary |
| `go vet ./... && gofmt -l .` | Lint; both must print nothing |
| `go test -race ./...` | Run all tests (they live only in `e2e/`) |
| `go test ./e2e/ -run TestSubscribeMovie` | Run one scenario |
| `docker build -t crychic .` | Build the image (distroless, uid 65532, data at `/data`); `compose.example.yaml` shows a deployment |
| `go test ./e2e/ -update` | Regenerate golden transcripts after an intended behavior change |

## Architecture

```
cmd/crychic/         # main: config.Load(os.Getenv) → app.Run
internal/app/        # the only wiring point; shared by main and e2e
internal/flow/       # platform-agnostic conversation: search → pick (library check) → season → confirm → subscribe
internal/moviepilot/ # minimal MoviePilot client, implements flow.Backend
internal/bangumi/    # Bangumi's public API (no key): airing calendar and synopses, implements flow.Calendar
internal/telegram/   # renders flow.Reply as messages + inline keyboards; whitelist check; delivers notices
internal/notify/     # remembers requests (data dir JSON), polls MoviePilot transfer history, notifies requesters
internal/config/     # env vars → config.Config
e2e/                 # behavior tests: real app vs fake Telegram Bot API + fake MoviePilot + fake Bangumi
```

Arrivals: `notify.Notifier` polls `GET /api/v1/history/transfer` → `arrive` records matches as pending (media + season + episode range, plus one source file name per download, at most 3) → `flush` announces once settled → each download's quality is read from MoviePilot's own release-name recognizer (`GET /api/v1/media/recognize?title=<file>`, what its WebUI shows; also a TMDB lookup, ~2 s, cosmetic within 10 s, unrecognized answers `meta_info: null`) and shown once as small print, e.g. `1080p · BluRay · x265 · FLAC 2.0 · FROGE` → `telegram.Bot.Notify` posts in the requesting chat, mentioning the requester in groups. Only the file name of `src` is kept, never the server path. Watches of the same media and season (a subscription and a download picked for it) match the same transfer, so `flush` tells them together: the first to settle announces every pending arrival of all of them in one notice, to all their requesters, once the media server shows every one of them (`due` checks the whole group, `settling.holds`); the notice says all wanted episodes are in only when that holds for every watch it tells, in a download's words only when every watch it tells is a download; a stuck download is likewise told once to every watch awaiting it (`withStalls`).

With `CRYCHIC_TELEGRAM_NOTIFY_CHAT_ID` set, `notify.Options.Destination` replaces requester delivery: one notice per watch delivery to the channel, with no requester identity and no fallback to the originating chats. Blank keeps the original behavior. The destination is a negative chat ID or `@channelusername`; the bot needs channel posting rights. Delivery still persists before sending and does not replay failed sends.

Data flow: Telegram update → `telegram.adapter` → `flow.Engine.Start/Choose` → `flow.Backend` (MoviePilot) → `flow.Reply` → `sendRichMessage` (command) or `editMessageText` with `rich_message` (button) → `answerCallbackQuery` last.

## Environment

- `CRYCHIC_MOVIEPILOT_URL`, `CRYCHIC_MOVIEPILOT_API_KEY` (MoviePilot `API_TOKEN`), `CRYCHIC_TELEGRAM_TOKEN` - required
- `CRYCHIC_TELEGRAM_ALLOWED_USERS` - required, comma-separated user IDs; empty refuses to start
- `CRYCHIC_TELEGRAM_API_URL` - optional, defaults to `https://api.telegram.org`
- `CRYCHIC_TELEGRAM_NOTIFY_CHAT_ID` - optional arrival channel, negative ID or `@channelusername`; empty notifies request chats
- `CRYCHIC_BANGUMI_API_URL` - optional, defaults to `https://api.bgm.tv`; the 新番放送 calendar is read from it
- `CRYCHIC_DATA_DIR` - optional, defaults to `data`; holds `requests.json` (pending requests, last seen transfer)
- `CRYCHIC_NOTIFY_INTERVAL` - optional, defaults to `1m`, minimum `100ms`; how often transfer history is polled
- `CRYCHIC_NOTIFY_LIBRARY_WAIT` - optional, defaults to `30m`, `0s` disables; how long a settled notice waits for the media server to show the arrival
- `CRYCHIC_PROGRESS_INTERVAL` - optional, defaults to `5s`, minimum `100ms`; how often a followed `/tasks` view refreshes (Telegram throttles frequent edits)
- `CRYCHIC_NOTIFY_STALL` - optional, defaults to `6h`, `0s` disables; how long a requested download may make no progress before its requesters (or the notify channel) are told once that it seems stuck
- `CRYCHIC_NOTIFY_QUIET` - optional, defaults to `3m`, `0s` disables; how long a show's arrivals settle before one notice covers them
- `CRYCHIC_NOTIFY_DIGEST` - optional weekly digest moment in China time, e.g. `sun 20:00`; empty sends none. Goes to the notify channel when set, else privately to each whitelisted user

## Code Style

- `flow` must never import a platform package; a new platform is a sibling of `internal/telegram` that consumes `flow` through a small interface
- Inject dependencies (`Backend`, `Now`, `*http.Client`, `*slog.Logger`); construct concrete types only in `internal/app`
- Buttons only choose (the one exception is a notice's `flow.Open` link, e.g. 在 Emby 中观看): no emoji, no titles or facts in labels. Picks are number buttons (`gridColumns` a row) or short names (第 N 季), with the details in the message text; menus share rows (`menuColumns`)
- Button rows run in one order: choices (numbers and their pager, seasons, 确认X on a row of its own), switches (电视剧/电影, weekdays; the shown one marked `·X·` by `markShown`), onward actions (搜索资源/相似推荐/同系列 via `onward`, 订阅历史, 重新搜索 on its own row), and last the one navigation row
- Navigation has one vocabulary. A request (search, subscribe, download, resubscribe) ends with 取消; a browsing screen (lists, details, charts, task views) ends with `browseRow`: 首页 then 关闭 (`c`, generic). Every way back is labelled 返回 (`labelBack`): navigate's history (`bk`, put in front of 取消/首页/关闭 by `withBack`) or `backTo` a list read afresh (tasks `l`, subscriptions `j`, history `hf`, charts `b`); a screen never shows two. Destructive confirmations are 确认X over 返回 alone
- Data with columns (season picker, multi-season results, a task's files or progress) is a `flow.Table`; the multi-season picker shows its ticks as `Ticked` lines
- Numbered list entries are `flow.entry` (an `Item` block): bold name, then facts (original title, year, kind, rating, state, progress) in italics below it, rendered as `<li value="n">` so numbers match the buttons on every page. Each message opens with a `Heading`; list sections and calendar dates are `Group`s, page numbers and refresh state are `Remark`s (footer), a media card's original title, year / kind / rating, genres / length and cast share one line of `Small` print (joined by ` · `) under its heading, and a media card is separated from its question by a `Divider`
- User-facing copy is `flow.Text` built with `Strong`/`Emphasis`/`Mono`/`Linked`/`Quote`; never put platform markup in flow strings, adapters render and escape. Emoji sparingly: 🔍 search, 🎬/📺 card, ✅ done, ℹ️ already subscribed, ⬇️/⏸️ download progress, 📦 transfer job (⏳ ▶️ ✅ ⚠️ per file), 📋 task list, 📥 arrival, ⚠️ errors, ⌛ expired, 🚫 refused
- Voice: the bot is cheerful and cute, calls itself 我 and the user 你, ends sentences with 啦/哦/呀/～. At most one kaomoji per message, only on home, success, empty/failed results and arrival notices (never in headings, toasts, tables or facts), from this set: `(๑•̀ㅂ•́)و✧` `ヾ(≧▽≦*)o` `(ﾉ>ω<)ﾉ` `(｡•́︿•̀｡)` `(´-ω-`)`. Data stays neutral (titles, facts, table heads, subscription states, 第 N 季, page numbers, file states, chart names, the 你请求的 tag), as do button labels and the command menu. Safety meaning never softens: an unknown subscription result still sends the user to `/subscribe` first, cancelling still says MoviePilot stops downloading, an API key refusal still names the admin; MoviePilot's own refusal messages are relayed verbatim
- Errors safe to show users are `*flow.UserError`; others get logged and shown as the generic outage text
- Hard limits: functions ≤ 50 lines, nesting ≤ 3, ≤ 3 positional params (use a struct, e.g. `moviepilot.call`), complexity ≤ 10, no magic numbers

## Testing

- **Agents never write to a real MoviePilot**: no `POST /api/v1/subscribe/`, no `POST`/`DELETE /api/v1/download/`, no resource searches (`/api/v1/search/*` queries the owner's PT sites) and no bot runs that end in a subscription or download. A real subscription makes MoviePilot search and download from the owner's PT sites and can get the account banned. Agents' live calls are limited to read-only metadata endpoints; write paths are verified through the fakes and MoviePilot's source. The owner may test the live bot by hand
- `transcript.verify` also fails any message the bot sends or edits whose content (posters aside) does not open with a `<h3>` heading: every message, endings, expiries and empty states included, opens with a `Heading` (`titled` adds one to a bare failure)
- End-to-end only: no unit tests, no mocks of internal packages, no redundant or change-detection tests
- Every scenario ends with `h.tr.verify(t)`; after `-update`, review the transcript diff line by line and commit it with the code
- Press buttons with `tap(user, msgID, label)` so a button missing from screen fails; use `tapData` only for deliberately stale buttons
- The fake Telegram accepts `answerInlineQuery` (results must be an array of articles with a 1–64 byte id, title and message text) and records every result with its text and buttons; `h.inline(user, query)` sends an `inline_query` update and waits for the answer
- `PUT /api/v1/subscribe/status/{id}` sets R/P/S for a subscription in the current list, which then lists it in that state (`fake_substate_test.go`), else answers 订阅不存在. The fake MoviePilot answers the library and downloader checks as an idle server (`idleServer`); scenarios override `libraryShowPath`/`libraryMoviePath`/`downloadsPath`. `DELETE /api/v1/download/{hash}?name=...` removes only that instance's task; omitting `name` selects the default qBittorrent, whose deletion succeeds even for an absent hash. A route for the exact path overrides that
- Recordings of `/api/v1/download/` carry tracker URLs with passkeys, the site name, the release name and the owner's username: keep only the fields Crychic reads
- Fakes must behave like the real services (long-poll `getUpdates`, `X-API-KEY` check, real error shapes); extend them, don't shortcut them

## Gotchas

- The API key authenticates as MoviePilot's **superuser**; every subscription is owned by the admin, not the chat user
- Media `type` is a Chinese enum: `电影`, `电视剧`; results without `media_source`/`media_id` are dropped
- Every JSON endpoint answers `{success, message, data}`, even where the route's `response_model` says `List[...]` (wrapped by `app/api/response.py`); `moviepilot.Client.do` unwraps it, and `success: false` on HTTP 200 becomes a `UserError` with `message`
- `GET /api/v1/subscribe/media/{id}` returns `data` with `id: null` when nothing is subscribed, not a 404
- Every message is a rich message (`sendRichMessage`; edits pass `rich_message`, and the library's empty `text` field is accepted). Media posters are an `<img>` block on top; search result, chart, 相似推荐 and 同系列 pages carry their entries' posters as `Reply.Gallery`, a `<tg-slideshow>` on top in list order (Telegram shows no per-slide captions, so slides carry no text). Telegram fetches posters itself the first time; every poster's `file_id` is then read from Telegram's copy of the message and later messages send it by `file_id` (`tg://photo?id=pN` media; transcripts normalize to the displayed image identity), so Telegram need not fetch it again. A refused message forgets the file_ids it reused and is retried once with its posters sent afresh, then without any poster (Telegram does not say which one failed; not for "message is not modified"). Douban images (`*.doubanio.com`, all Douban charts and 正在热映) answer 418 without a Douban referer, so Telegram cannot fetch them: `internal/telegram/posters.go` downloads them with the referer and its own User-Agent (`img3` answers 403 to Go's default one; 5 s budget, 5 MB cap, 4 at a time), uploads them as `attach://` media (file_ids: memory only, LRU of 1000, gone on restart); a poster that fails to download is dropped alone. MoviePilot's WebUI shows them through its own image proxy (`/api/v1/system/img`), which Telegram cannot reach. Rich HTML collapses newlines, so the renderer turns them into `<br>`. The home menu alone sets `Reply.Banner` (`flow.BannerHome`; every name in `flow.Banners` needs a bundled JPEG or the bot stops at start); the banner goes through the poster file_id cache as `banner:<name>`, uploaded once and then reused like a poster. Empty feature buttons only flash a notice and leave the home banner untouched. Telegram clients often keep showing the old top image after an edit changes it until the chat is reopened; the bot's requests are right, and the owner chose not to work around it. Photo messages (home menus from before rich messages) cannot become rich text, so a press on one sends a new message and deletes the photo; photos are recognized from callback metadata; `Reply.Notice` keeps them untouched
- Poster URLs from MoviePilot are TMDB `original` size (MBs); `moviepilot` rewrites them to `w500` (`posterURL`)
- `GET /api/v1/media/{id}` details are cosmetic: on failure the card falls back to search metadata and the flow continues; its `directors` field mixes in producers and episode directors, so it isn't shown
- Subscriptions take `start_episode` (per season): MoviePilot skips earlier episodes. "只追新集" uses details' `next_episode_to_air` and only shows when it is in the chosen season and > 1; button data `ok:<n>` carries the start, validated against the season's episode count before the confirmable target is cleared
- The bot registers its command menu (`setMyCommands`, `telegram.commands`) on every start, for the default scope and for each whitelisted user's chat (a chat-scoped menu outranks the default; the owner's token carried a stale one from an earlier program); keep it in step with `parseCommand`'s commands and `help`
- Explicit commands for another bot (`/search@other_bot`) are ignored before dispatch or refusal. Forum destinations persist in `Actor.Address` as `chat/topic`; ordinary numeric addresses and channel usernames remain compatible. Only a positive `message_thread_id` on `is_topic_message` selects a forum topic. Commands, callbacks, typed answers and notices preserve it; pending input is keyed by chat, user and topic.
- Telegram keeps the last `allowed_updates` a `getUpdates` sent and go-telegram/bot omits it by default, so the bot sends its own list (`telegram.allowedUpdates`: message, callback_query, inline_query); the owner's token was left at message + callback_query by an earlier program, which silently dropped inline queries. The fake Telegram starts with that stale list and honors `allowed_updates` like Telegram; a new update type must be added there or it never arrives
- A sent reply (not only an edited one) with `Follow` gets a follower (`adapter.replyTo`), and so does a typed answer's edit (`adapter.show`, shared with button presses), e.g. `/search 下载 <title>` with a unique result whose resource search starts at once; 重新搜索 is not offered on a search under way
- A follower keeps one unsent `Reply` until its edit succeeds (including `message is not modified`). Delivery failures retry that reply, never the flow transition or resource search, on the existing refresh cadence and respecting Telegram's `retry_after`; retries stop after `FollowFor` from the first failed delivery. Owner navigation or cancellation discards the pending reply. A callback suspends its follower before waiting for the message lock, but a rejected callback resumes the same follower and pending reply; an intervening accepted navigation invalidates that identity.
- Typed answers: a `Reply` with `Input` makes the Telegram adapter remember (chat, user) → message in `adapter.pending`, including initial sends. Private chats take plain text as an answer while pending, otherwise search it as a title; every recognized private command clears the old pending input. An expired prompt leaves unquoted private text free to start a new title search immediately; an explicit quoted answer only reports expiry. `Reply.Expired` carries this semantic distinction without inspecting rendered text. Typed episode numbers accept full-width digits and the optional 第...集 wrapper, then use the same range checks. Private text/commands share an input lane so old answers cannot restore a cleared prompt. Groups only take a reply quoting the prompt
- Resource search is `GET /api/v1/search/media/{id}?media_source=&mtype=&season=` (MoviePilot searches every indexer site while the request waits, tens of seconds; `torrentSearchTimeout`), answering `Context.to_dict()` items; nothing found is `success: false`, 未搜索到任何资源. Their `torrent_info` carries the site's cookie, user agent and download link: `moviepilot` keeps `media_info` + `torrent_info` raw as `flow.Torrent.Record`, which is never shown, logged or persisted, and `POST /api/v1/download/` gets it back unchanged as `{media_in, torrent_in}` like the WebUI; the answer's `download_id` is the torrent hash. A download's watch (`Request.Download`, `watch.Download`) matches transfers by `download_hash` and its season, takes every file of that download and ends when the whole season arrived (not the release's episode range: MoviePilot also reads episodes from the description, so a 25-episode pack saying 「修复第9集章节」 is E09 in its search results and download history, and `/tasks` shows that label), else settles after quiet, or `orphanGrace` after the download left `GET /api/v1/download/`; stall notices match it by hash
- MoviePilot has no outgoing webhook, so arrivals come from polling successful transfer history (one record per file, `seasons` "S03", `episodes` "E01" or "E01-E03"). v3.1.0 sorts by local completion `date` (`YYYY-MM-DD HH:MM:SS`), not ID, and a failed transfer succeeding on retry updates the same row's date/status. `TransferCursor` persists that date and all successful IDs seen in its second; reads include the entire boundary second across pages. The first poll records the whole newest second as baseline, so earlier history is never announced. The bot compares MoviePilot's civil dates as written, not with its own clock. The catch-up remains bounded; an incomplete newest second at that bound is an error, never a committed checkpoint.
- Old notification files with only `baseline`/`last_transfer` migrate in one atomic state update: still-unseen IDs above the old watermark are processed once, all currently read successes seed the date cursor, and pending notices, requests and digest entries are preserved. Ambiguous older IDs are not replayed during migration; low-ID successes already missed before upgrading cannot be reliably distinguished from previously processed history. An initialized empty cursor is persisted too, so the first later arrival is not swallowed as another baseline.
- MoviePilot closes a subscription when downloads finish, before files are transferred: a closed subscription must not immediately end a watch. A completed download watch ends after its notice; a subscription watch keeps its requesters and delivered episodes until `orphanGrace` (72h) after its subscription disappears. This preserves controls for active upgrade subscriptions and notices for seasons whose episode counts grow. A watch whose row was last read gone is `closed`: its last total bounds episodes again, other downloads of a delivered movie or a complete season no longer count for stall notices, and a new request reusing its id (nothing pending) replaces it instead of inheriting its requesters.
- Before collecting new transfers or completing pending arrivals, the notifier reads their subscriptions and refreshes the current total and `best_version`. A failed read preserves the cursor and pending state for a read-only retry; a successful empty/replaced row preserves the last known scope. The initial `Target.BestVersion` is persisted, so upgrades still notify when the backend closes the row before transfer. New upgrade transfers may announce an already-delivered episode again, but the transfer cursor prevents replay; TV upgrade notices never infer complete upgrading from previously held episodes. Ordinary movies retain a delivered marker and notify once.
- A subscription watch is identified by its row id **and** media source, media id and season; SQLite can reuse a completed row id while its older files still await arrival. `withRequest` keeps those targets separate, and derived `watch.key` values keep their library waits and activity independent. `Feed.Subscription` reads the current row's identity from `GET /api/v1/subscribe/{id}`: a replacement does not keep the older watch active. `Watcher.Forget` takes the cancelled `Subscription`, not just its id, so it removes only that target. The persisted fields are unchanged; existing watches need no migration, but a new target already lost by the old id-only merge cannot be reconstructed from that state.
- MoviePilot transfers episodes one by one as their downloads finish, often minutes apart. A show's arrivals stay pending (persisted) until nothing new came for `CRYCHIC_NOTIFY_QUIET`, then go out as one notice; a watch whose every wanted episode is in (and any movie) is announced at once. The e2e default is `300ms`; `transfers` waits until a whole poll handled the records, so a test can act between polls
- A settled notice is held until the media server shows the arrival (`exists_remote`/`notexists`; rclone/alist dir caches can delay Emby by minutes), at most `CRYCHIC_NOTIFY_LIBRARY_WAIT`; the notice then links to the item from `GET /api/v1/mediaserver/latest` (matched by title + year; `link` is the server's public web URL, item `image` is an internal URL and is not used). The fake media server shows every transfer on top of the scenario's library fixture; `scenario.lagging` + `h.catchUp` model a server that has not scanned yet. Library and latest reads are polled, so they stay out of transcripts
- The fake answers `recognize` per file name (`scenario.recognized`, others get `recognize_none.json` like live); fake transfers carry `Src`/`Hash` only where a scenario needs qualities. History is filtered by status and paged by `Date`, with no assumed ID order between completion times. `failedTransfer`/`retryTransfer` model a failed row becoming successful without changing its ID; failed records are not visible in the fake media library. Only page-one reads advance the harness's full-poll barrier.
- Notifier state is saved before notices are sent: a crash may drop a notice, never repeat one. Polling calls are kept out of e2e transcripts; the notices they cause are recorded
- Button data is `<session>:<action>:<arg>` and must stay ≤ 64 bytes (Telegram limit). Guarded write buttons (`needsTicket`: `finishing`'s `ok`, `y`, `td`, `tz`, `bo`, plus subscription `sp`, `sr`, `z`) carry a fourth part, a ticket `navigate` hands the shown screen (`ticketed`); only a press with the shown screen's ticket writes, and 返回 restores a screen with its ticket, so a stale 确认 from an earlier pick of the same list never confirms the next pick. Subscription mutations do not enter `finishing`, which controls request navigation. An expired button only has its action to go on: task-specific actions point to `/tasks`, subscription-specific actions to `/subscribe`; ambiguous 返回/翻页 (`bk`/`p`) point to `/start` to reopen the relevant feature rather than claiming the page was a search
- The fake numbers subscriptions created from `subscribe_created.json` 1, 2, 3, ...; unlike an ever-increasing counter, MoviePilot's SQLite row ids can be reused after deletion, which `subidentity_test.go` models by replacing the listed record and `notify_identity_test.go` by returning the reused id to a new request. Reads by subscription id return the created/found identity (empty when absent); exact routes can model completion or replacement. The fake likewise answers each added download with its own hash (`addedHash`, then `addedHashN(n)`)
- Cancel/close and replacing a search use `store.take`. Confirmations use `settle`, which clears the target under the session's step lock before writing. Direct requests keep a terminal receipt without buttons until TTL; requests from lists keep navigation. A second tap only flashes a notice and cannot replace the outcome. 重新订阅 keeps its session for 返回 to the history: steps of a session run one at a time and it clears the confirmable target before writing, so a second tap only gets a notice. Failed reads clear the confirmable target but keep their context; only the failed read is repeated, and success clears retry state. Failed writes consume the confirmable target too, preserving a safe MoviePilot refusal or reporting an unknown result to check with `/subscribe`
- Unique ordinary search results open directly, but chart identity disambiguation still requires a pick. The season picker is skipped for the season a search term named (`Media.Season`, from MoviePilot's search `season`, when the show has it; 青之芦苇 第二季 opens on 第 2 季) or a sole season whose number is positive; specials are never selected implicitly. TMDB may fold a sequel into season 1 (青之箱 第二季 continues at S1E27), which then opens like any sole season. Both shortcuts keep final confirmation. `重新搜索` (`rs`) replaces the old session when the new title is submitted; empty results keep a typed-title prompt. Generic paging records its screen, so 返回 restores the page selected from
- Session IDs are random across restarts; never replace them with a counter that resets on startup. `Choose`/`Answer` validate both user and chat and serialize steps per session. Calendar annotations clone both mutable slices before writing. E2E transcripts normalize opaque session IDs only when recording, never in updates sent to the app
- Subscription buttons (`sd`, `su`, `sp`, `sr`, `v`, `z`) carry the subscription id, never an index into the session's list (`session.subAt`). Row ids can also be reused: `subidentity.go` checks the displayed subscription's source, media id, kind, season, episode group and original creation `date` (`Subscription.Created`) against a fresh list before pause, resume or cancellation; an unavailable or changed identity only flashes a notice, never writes. Details use the same identity comparison. `Watcher.Requested(userID, subs)` checks the watch's media and season as well as its id, so reloading a reused id does not grant ownership of another target. MoviePilot's write API has no conditional identity parameter: these are client-side preflight checks, not an atomic compare-and-write guarantee against concurrent backend replacement.
- Release-name technical numbers are masked without consuming their boundaries (`moviepilot.withoutTechnical`); adjacent audio tracks such as `FLAC.2.0+5.1` share a separator, and neither may become an episode token. Numeric boundaries are checked against the original title so fragments of years or resolutions are not removed.
- Callback action strings are unique across every flow handler. Resource search is `ts`/`tg`/`tr`/`tq`, release pick `tp`, ticking releases `tm`/`tk`/`tb`/`tz`, release order `to`, site filter `tf`/`tw`, missing-only filter `tx`, download `td`, download deletion `kd`/`ky`; 洗版订阅 is `bv`/`bo`, subscription return is `j`, subscription kind `sf`, shared cancel `sc`, subscription details/refresh `sd`/`su`, pause/resume `sp`/`sr`, history `hs`/`hf`/`hp`/`ho`, calendar weekday is `w`, generic list paging is `p`, 相似推荐 is `r`, 同系列 is `n`, 重新搜索 is `rs`, read-only 重试 is `rt` and 返回 is `bk`
- MoviePilot calls are bounded per call (`moviepilot.callTimeout`, 30 s; resource search `torrentSearchTimeout`, 2 min), so its `http.Client` sets no `Timeout`. A call whose body carries site credentials (`call.secret`, the download post) never quotes MoviePilot's error answer, which can echo the request. An owner's button press stops the message's follower before waiting for the message lane, so a slow refresh never holds the press
- Telegram non-poll requests have a 10-second deadline including response-body reads; `getUpdates` uses the HTTP client's 70-second timeout. Metadata card enrichment uses a 5-second cosmetic budget; independent read-only calls overlap (a show's seasons are read alongside its details and library state). The Telegram adapter counts running handlers and followers and `Bot.Run` waits for them after polling stops, since the library does not, subscription writes do not. All clients share one transport keeping 16 idle connections per host
- List pages budget text and item buttons together (up to 20 entries and 3000 content runes). Large transfer views show at most 100 file lines, retaining the full aggregate count and explicitly naming omitted files
- `LibraryWait=0` bypasses media-server checks. Movies and complete seasons start that wait immediately; incomplete seasons start after quiet. Unchanged notifier state is not rewritten; necessary writes remain serialized under the state lock
- A `Reply` with `Notice` must not edit the message (another group member tapping your buttons)
- Library checks go through MoviePilot to its media server and are cosmetic like details (failure does not block confirmation, but the card marks the library state unknown instead of claiming absence). Shows use `POST /api/v1/mediaserver/exists_remote` (`{"3":[1,2,...]}`, `{}` when absent; needs `title`+`year`, ids alone answer `{}`). Its episode lists are sorted and deduplicated at the client boundary: media servers can return several unmerged versions of one episode, which must not count as several episodes or make a missing season look complete. Movies use `POST /api/v1/mediaserver/notexists` (`[]` = held), because `exists_remote` answers `{}` for movies either way. `GET /api/v1/mediaserver/exists` reads MoviePilot's own sync table, which is empty unless library sync runs, so it isn't used
- `GET /api/v1/download/` lists unfinished torrents; `media` (source, id, `season` "S01", `episode` "E10-E12" or "E02、E04-E05", parsed segment by segment without filling gaps) comes from MoviePilot's download history and is null for torrents added by hand; `progress` is a percentage, `size` the bytes of the files being downloaded (qBittorrent `total_size`; shown in `/tasks` as e.g. `17.5 GiB`), `state` is `downloading` or `paused`, `left_time` is Chinese text like `1时5分3秒` (empty while stalled). The card shows the chosen target's downloads, cosmetic like details
- `/tasks` follows a task by re-reading `GET /api/v1/download/` (by downloader instance and torrent hash, `flow.DownloadRef`) or `GET /api/v1/transfer/queue` (by media + season; tasks are `waiting`/`running`/`completed`/`failed`, each file covers `meta.begin_episode` through `meta.end_episode`, inclusive; a missing end means one episode). Byte progress of a transfer is only an SSE stream behind a browser cookie (`/system/progress/filetransfer`), so transfers show per-file states. A view stops when its task leaves the list, when its owner presses 停止刷新, or after `flow.FollowFor` (10 min); any button press on a followed message cancels its follower first. Every task view has 返回 (`l`), which re-reads both lists in the same session (a finished view keeps its session for that). Both lists are polled, so the fake keeps them out of transcripts and `reports` swaps their fixture
- `GET /api/v1/download/` aggregates tasks from all configured downloaders. Deletion must preserve each task's `downloader` and send `DELETE /api/v1/download/{hash}?name=<instance>`; omitting `name` selects the default instance. It always deletes files too (`delete_file=True` in v3.1.0) and answers only `success`; qBittorrent reports success even for an absent hash, so that response cannot correct a missing instance selector. Instance names stay out of messages and buttons. Deleting does not undo a subscription: its `note` recorded the episodes as obtained when the torrent was added, and nothing in MoviePilot's core listens for the deletion, so the subscription never fetches them again
- `GET /api/v1/subscribe/` lists all subscriptions for the superuser key (`state` N/R/P/S, `lack_episode`, `total_episode`); Crychic filters it to movie/TV records, never treating music or unknown types as movies. `Backend.FindSubscription` retains both ID and state, so an existing paused subscription card says 目前已暂停; `DELETE /api/v1/subscribe/{id}` answers 404 for one already gone, which `Unsubscribe` treats as done. Deleting a subscription only reduces downloads; the bot's other live writes are subscribing (and resubscribing), pausing/resuming a subscription, downloading a picked release and deleting a download
- Subscription details show what applies where a subscription sets nothing: no quality/resolution/effect is 不限, and no `filter_groups` falls back to the global `SubscribeFilterRuleGroups` setting (`GET /api/v1/system/setting/SubscribeFilterRuleGroups`; the per-kind default subscription configs only seed new subscriptions). MoviePilot schedules no search per subscription (`execution_status.next_run_at` is null after a run), so 自动查找 reads its scheduler (`GET /api/v1/dashboard/schedule`, the WebUI's 后台服务): `subscribe_refresh` browses the sites' newest releases (`SUBSCRIBE_MODE`, every `SUBSCRIBE_RSS_INTERVAL` minutes) and `subscribe_search` only exists while `SUBSCRIBE_SEARCH` is on; `next_run` is Chinese text such as 19分钟, status 等待 or 正在运行. Both reads are cosmetic, inside the details' budget (`flow.SubscriptionUpkeep`); `schedule.json` and `subscribe_filter_groups.json` are trimmed live recordings
- Only the subscription list attaches `execution_status`; `GET /api/v1/subscribe/{id}` does not. `last_search` and execution `next_run_at` are UTC timestamps, displayed in China time; missing/unrecognized timestamps and states stay unknown. MoviePilot v3.1.0's execution-error projection only flattens/truncates text, so it can still contain paths or credentials: `moviepilot` passes only `HasError` to flow, never the original error. `subscriptions_details.json`, `downloads_subscription.json`, `queue_subscription.json` and `library_subscription.json` are synthetic v3.1.0-shaped e2e fixtures, including an intentionally private-looking error to prove it is not shown
- Chart picks (`/api/v1/recommend/*`) are search-shaped but Douban/Bangumi ones carry Douban/Bangumi ids, while transfer history only carries TMDB ids; a pick is therefore searched by title (its original title searched at the same time, used only when the title finds nothing) and only taken directly when the identity or a unique title+year+kind matches, else the user picks. Douban season titles like 「流人 第六季」 often find nothing right. MoviePilot's Bangumi calendar (`/api/v1/recommend/bangumi_calendar`) loses the weekday grouping and serves 30 items a page (Monday to Wednesday), so the bot reads `api.bgm.tv/calendar` itself (summaries there are always empty; synopses come from TMDB, else Bangumi's subject API directly). A TMDB twin keeps its pick's `Weekday` and air date. Fake routes are keyed by path, so a scenario needing two searches swaps `searchPath` with `h.mp.setRoute`, or answers per title with `scenario.searches`. Reads the bot makes at once (calendar lookups) arrive in any order, so the transcript sorts each run of consecutive reads of one route (`transcript.settle`; media searches and details count as one route, searches first; the calendar's TMDB season reads count as one route too)
- 相似推荐 reads `GET /api/v1/tmdb/recommend/{tmdbid}/{电影|电视剧}` (TMDB media only; `type_name` must be the Chinese enum, `movie` answers 未知错误); `/tmdb/similar` is not used, its picks are poor. MoviePilot's details leave `collection_id` null (it reads TMDB's `belongs_to_collection` under the wrong name and drops `tmdb_info`), so 同系列 searches collections (`/api/v1/media/search?type=collection`, items `type` 系列) by the movie's titles and their stems (沙丘2 → 沙丘, `Dune: Part Two` → `Dune`), searches every name at once, then opens up to 3 candidates per name at once (`/api/v1/tmdb/collection/{id}`), and takes the first listing the movie in name order (a failed read before it is the answer); a series named unlike its films (哈利·波特与魔法石) is not found. The fake answers collection searches per title (`collectionSearch(title)`, `[]` otherwise, like MoviePilot), and the transcript sorts them like other simultaneous reads
- MoviePilot counts episodes as obtained once their torrent is added and closes the subscription then; it never checks progress (`chain/subscribe/completion.py`), so a dead torrent would end in silence. Each poll also reads `GET /api/v1/download/`: a non-paused download of a watched media/season (and, when known, a still-missing episode) whose progress has not changed for `CRYCHIC_NOTIFY_STALL` is told about once (`internal/notify/stall.go`). MoviePilot v3.1.0 collapses queuedDL into downloading, so the reminder says long without progress and names queuing as a possibility, not a proven dead torrent. Progress marks live in memory (a restart restarts the clocks, so no state write per poll); the told torrent hashes persist in the watch (`stalled`), so a restart never repeats a stall notice
- Held episodes never appear in transfer history, so a `Request` carries `Held`. Subscription watches count them as delivered; download watches persist them separately (`held`) and use their union with actual arrivals only for completion, so re-downloaded episodes still announce. An already fully held season does not seed Held for a replacement download. Completion that used prior holdings says so, but does not retire the download watch before its own files cover the season (or orphan grace expires), so later replacements of previously held episodes still notify; old requests without Held are readable but cannot have the missing observation reconstructed
- When MoviePilot behavior is unclear, read its source (`app/api/endpoints/{media,subscribe}.py`) instead of guessing

## Workflow

- Commit each finished task on its own; never push unless asked
